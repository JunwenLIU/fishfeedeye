## 0. 拍板结论（先看这一节）

### 0.1 一句话技术栈

> **Python 3.11 + PyTorch(CUDA 12.6) + Ultralytics YOLO11m/YOLO26 + Roboflow Supervision + SAHI(切片推理) + OpenCV（透视校正/参考区噪声扣除） + Gradio 本机 Web UI + pingouin/statsmodels 统计层，输出 CSV + Matplotlib 图表。**

### 0.2 五个必须回答的问题

| 问题 | 结论 |
|---|---|
| **有没有现成的「鱼类摄食分析」开源项目能直接 fork？** | **没有。** 我用 GitHub 搜索 API 扫了 `fish feeding detection` / `fish behavior tracking` / `aquaculture yolo` / `fish appetite` 四组关键词，最高星的项目只有 13 星，其余全是 0–2 星的本科毕设级仓库。**必须由通用组件拼装。** |
| **通用 YOLO 权重能不能零训练跑？** | **不能。** 关键事实：**COCO 的 80 个类里没有 `fish`**，更没有饲料颗粒。拿 `yolo11n.pt` 直接跑，鱼和饲料都检测不到。这是本项目最大的认知陷阱。 |
| **那零训练冷启动怎么办？** | 走 **「鱼体无关型传统 CV 特征 + ROI 标定」** 兜底：颗粒用背景减除+斑点检测（**两步法**：先扣动物掩码、再限定投饵板 ROI），活跃度用光流/帧差能量/**反射波纹傅里叶频谱**（**后者完全不需要检测到鱼，专治高密度看不清**）。**不需要任何训练数据，当天就能出颗粒衰减曲线与活跃度曲线**；同时用 **YOLOE 开放词汇检测** 做语义辅助。详见 §3.4。 |
| **要不要训练？要多少数据？** | **要，但很便宜。** 推荐 **30–80 帧人工标注微调**（约 1–2 小时标注），在用户的 RTX 3060 Ti 上训练 10–20 分钟，即可从"能跑"升级到"能横向比较"。**该阶段解锁 P0 主指标「投喂区鱼数占比 / RP」**。详见 §3.4、§3.5。 |
| **用户本机算力够不够？** | **够，而且远超需求——算力根本不是瓶颈。** 实测本机有 **RTX 3060 Ti 8GB + CUDA 12.6**；但**当前装的是 CPU 版 PyTorch**（`torch 2.6.0+cpu`），**必须重装 CUDA 版**。改用变间隔抽帧后，20 分钟视频仅需 ~156 帧，推荐配置下 **约 4 秒跑完**。**省下的算力应全部投向精度**（更大 imgsz、开 SAHI、多尺度 TTA）。详见 §1、§3.6。 |

### 0.3 四条不做的事（避免踩坑）

1. **不做视频时序模型（SlowFast / VideoMAE / TimeSformer）**。理由见 §2.4：这是"细粒度小样本 + 需要可解释数值输出"的任务，时序模型要几百个标注视频段、且给不出"剩余颗粒数"这种数值指标。**性价比极低，明确否决。** 摄食起止时刻改用**光流信号阈值 + 持续性判据**划定（§3.4）。
2. **不做鱼体关键点/姿态估计（DeepLabCut / SLEAP / MMPose）**。理由见 §2.5：需要逐条鱼标注关键点，标注成本比框高 5–10 倍。摄食强度用**活跃度 + 聚集度**两组统计量代理即可。
3. **不上 Roboflow 云端训练托管**。用户数据在本机，Ultralytics 本地训练已足够简单；Roboflow 只用来**下载公开数据集和预训练权重**（免费账号即可）。
4. **（v2 新增）不建议用户加装亚克力/玻璃罩隔绝反光**。ShrimpFarming 实测该方案**已被废弃**：亚克力表面瑕疵导致持续失焦模糊，拉开距离改善清晰度后反光噪声又回来。**改用偏振镜（CPL）+ 把投饵板置于反光最小区域。** 详见 §3.3。

### 0.4 本项目的真正难点（v2 新增，请团队与用户都先读这一节）

> **2025 年最新的、专门做"饲料诱食性评估"的工作（Sensors 2025, 25(1):248），最终也只做了定性分析。**
> 论文摘要原文：*"…relying on a **qualitative analysis** due to **the challenges of defining suitable quantitative metrics**… highlighting the need for further investigation."*
>
> **这说明"定义可复现的定量指标"本身就是难点，也正是本项目最大的价值所在。**
>
> 由此推出三条工程纪律，必须写进架构：
> 1. **每个指标都必须带质量分与适用条件**（如 ID 切换率、N₀ 双轨偏差、密度等级），**不允许输出无质量标注的裸数值**。
> 2. **跨组比较必须锁定同一套参数**（`run_config.yaml` 是硬约束，不是可选项）。
> 3. **能力要有降级开关**（§4.3.1 密度矩阵）：高密度/浑浊时，主动关闭不可靠指标并明示，而不是硬凑数。
>
> **宁可少输出几个指标，也不要输出看着漂亮但不可信的数字——这会直接毁掉用户拿它做饲料对比决策的前提。**

### 0.5 四条设计原则（v7 新增，与 PM 四轮交叉核验的共同产物，**建议原样写进 PRD 非功能需求**）

四轮交叉核验中，双方互相纠错 11 次。PM 的总结很准：

> **"我们反复抓到的不是『算错』，而是『算对了但意思错了』。"**

五个实例全部符合这个模式：

| # | 实例 | 数值对了吗 | 错在哪 |
|---|---|---|---|
| 1 | `trustworthy` 布尔列 | 对 | **名字承诺了没验证的事** |
| 2 | 1 Hz 重采样 | 对 | 数值正确但被下游当成**真实观测点** |
| 3 | 用 0 冒充空值 | 对 | **语义错**（0 是有意义的数值） |
| 4 | 未版本化的阻断清单 | 单次都对 | **跨批不可比** |
| 5 | 跳过密集帧的验证 | 对 | 得出**漂亮但无意义的误差** |

**共同点：值本身没问题，问题出在它被下游解读时丢失了适用边界。** 由此归纳四条原则：

1. **不得给出无法兑现的承诺。**
   不给 `trustworthy` 这类名字、不给未标定的"已验证"指标、不给未校正的"已校正"结论。**判定标准：如果我们的结论依赖一个我们没有的机制（真值对照、人工核验），就不能说。**

2. **边界处不得使用有语义的默认值。**
   不用 0 冒充 None、不硬编码 `v_sink_max`、计数列不得让"空"排在最前、**误差低于噪声下限时不得报"误差≈0"**。

3. **任何影响"跨批次可比性"的决策都必须版本化并参与比较校验**（PM 提出，我补充落地）。
   **判定标准：如果它变了会让两次运行的结果不可比，它就必须进 `run_config` 并被 `compare.py` 校验。**

4. **⭐ 数值必须与其适用边界一同传递，边界不得只留在文档里**（我对上述五例的统一解释）。
   `MetricValue`（value + status + reason + flags + unit_scale）、`metrics_spec_version`、`flag_glossary.csv`、验证报告的"噪声下限并列展示"——**这四处是同一条原则的四个落点**。
   **判定标准：如果一个数值离开本文档后，接收者无法独立判断它是否可用，我们就漏了边界。**

5. **（v12 新增）schema 中的每一列都必须声明消费方与消费时机；没有消费方的列不进 schema。**
   实例：`window_s`（有数据无规则，PM 认领）、`blocking_flag_count`（有列但排序陷阱未处理，我认）、`ci_low`/`ci_high`（有占位无机制）、**`confidence`（PM 自查删除，见 §4.7）**。
   **判定标准：加一列时，必须能说出"哪个模块或哪类用户在什么时机会读它"。说不出就不加——它只会让 CSV 变宽，不会让结论变可靠。**

6. **（v12 新增）禁止"可信度摘要标量"。**
   **凡是形如"可信度/置信度"的单一标量（布尔或 0–1 浮点），若无法给出明确定义与消费方，一律不进 schema。**
   实例：**`trustworthy`**（布尔，被我否掉）、**`confidence`**（0–1 浮点，PM 自查后删除）。
   > 这类标量的本质是**把 `status` + `flags` + `quality` 三个结构化字段压缩成一个数**——**信息必然丢失，且用户会过度信任它**。
   > **判定标准：如果需要一个"能不能用"的筛选器，用 `blocking_flags` 这样的结构化字段，不要造一个数。**

> **这两条是同一个盲区的两个切面**：第 5 条管"列该不该存在"，第 6 条管"这一列是不是在假装知道它不知道的事"。**`confidence` 同时违反了这两条**——既无消费方，又是一个无法定义的信任度数值。

> **配套机制**：对 **指标定义 / 输出 schema / 阻断清单 / 阈值默认值** 四类改动保留一轮交叉 review。**其他改动不必**——否则流程成本会压垮效率。

### 2.3 视频行为识别 / 时序模型（**明确否决**）

| 项目 | GitHub | Star | 最后提交 | License | 可行性评估 |
|---|---|---|---|---|---|
| MMAction2 | `open-mmlab/mmaction2` | 5,145 | 2026-03-18 | Apache-2.0 | ❌ 否决 |
| MMDetection | `open-mmlab/mmdetection` | 32,894 | 2024-08-21 | Apache-2.0 | ❌ 不需要（Ultralytics 已覆盖） |

**否决理由（写给 PM 与用户看，很重要）：**

1. **任务性质不匹配。** 摄食强度分级是**细粒度、弱标注、小样本**任务。SlowFast / VideoMAE / TimeSformer 是为 Kinetics 这类"数百类、每类数百视频段"的粗粒度动作识别设计的，需要 **≥ 数百个标注视频片段** 才能收敛，用户拿不出。
2. **输出形式不匹配。** 用户要的核心指标是「**剩余颗粒数随时间的衰减曲线**」「**清空时间 T80/T95**」这类**连续数值与统计量**。时序分类模型只能吐一个"强/中/弱"的类别标签，**给不出曲线**，也解释不了"为什么"。
3. **可解释性与可信度。** 饲料诱食性比较是要给用户客户看的结论。"检测→计数→拟合衰减曲线"的链路每一步都能可视化、可复核；端到端神经网络的黑箱结论在科研汇报场景下说服力弱。
4. **性价比。** 检测+统计后处理用 YOLO11m 在 3060 Ti 上跑完 20 分钟视频约 4 秒（变间隔抽帧后）；VideoMAE-large 训练+推理成本高一个数量级，且精度未必更好。

> **学术上确实有人这么做**（Dong et al., PLOS ONE 2024，三流网络判别摄食强度 99.3%；Ni et al., Computers and Electronics in Agriculture 2024，运动影响图+改进动能模型 96.94%）。**注意：这两篇的方法本质都是「光流/运动能量等手工特征 + 浅层分类器」，不是端到端时序大模型**——这反过来印证了我们的路线：手工/统计特征 + 检测，是对的。

> **（v2 新增）2026 年最新证据进一步坐实该判断：** **EfficientFeedingNet**（*Animals* 2026, 16(5)）用**帧对光流 → 运动强度信号 V-Value** 自动划定摄食区间，准确率 **96.53%**，Jetson Orin NX 上 **143 fps**。
> 两条关键含义：
> 1. 其核心仍是**「光流统计量 + 浅层网络」**，不是端到端视频 Transformer。
> 2. **其 V-Value 驱动的自动标注，比人工标注数据集高出 13.13–18.46 个百分点** —— 说明**人工主观标注本身就是噪声源**。
>    → **工程落地：我们的"摄食起止时刻"不训练模型预测，改用光流/帧差能量信号阈值 + 持续性判据划定**（判据见 §3.4）。零训练、可解释、阈值可调。

> 1. 相机固定，背景可用背景建模减除，颗粒是**高对比前景**，标注极快；
> 2. 单图标注量虽大（~100 个颗粒），但可用 **SAM 2 半自动标注** 或 **"人工标 1 帧 + 模型预标 + 人工修正"的迭代法**；
> 3. 所需帧数少（30–80 帧足够起步），因为场景单一。

#### ⚠️ ShrimpFarming 论文的三条可直接抄的工程教训

| # | 教训 | 对本项目的落地 |
|---|---|---|
| 1 | **变间隔采样协议**：测试集为前 2 min 每 4 s、2–4 min 每 8 s、4–20 min 每 1 min，明确为"强调投饵后早期摄食瞬间" | **`ingest.py` 必须支持变间隔抽帧**，不要固定 FPS。（ShrimpFarming 协议下 20 min 视频仅 **61 帧**，而固定 5 FPS 需 6,000 帧——**差约 100 倍**）见 §3.6 修正后的性能预估 |
| 2 | **颗粒检测的两步法**：单独 HSV 色域分割颗粒会在光照变化时失效、并误检虾体与阴影；**改进为"先减去已分割的动物掩码，再限定投饵板 ROI 掩码内检测"** | **直接进 `filters.py`**。这是解决 §4.3 难点 #3（颗粒 vs 粪便/气泡误判）的现成方案 |

> **一条必须写进 §0 的反面证据（PM 提供）**：
> 该论文摘要原文——"proposes two approaches to evaluate pellet attractiveness, **relying on a qualitative analysis due to the challenges of defining suitable quantitative metrics**… **highlighting the need for further investigation**."
> **2025 年最新的、专门做这件事的工作，最终也只做了定性分析。** 这从反面坐实了本项目最大的价值点：**"定义可复现的定量指标"本身就是难点，也是我们的护城河**——因此每个指标都必须带质量分与适用条件，不可轻率输出。

### 3.4 ⭐ 冷启动方案（本节是全文最重要的结论）

#### 先说破一个误区

> **「用通用 YOLO 权重 + 规则法零训练跑出可用结果」——对本项目的鱼检测部分是不可行的。**
> 原因：COCO 80 类里**没有 fish**。YOLO11n/YOLO26n 的 COCO 权重里没有"鱼"这个概念，喂进去视频什么也检不出来。
> （Ultralytics 文档里确实有 "Fish Tracking" 的 demo 图，但那是**用鱼数据集微调过的模型**，不是原生 COCO 权重。）

#### 推荐的三层冷启动架构

> **（v2 修订）第 0 层已升级为「鱼体无关型特征」为主，不再是单纯的背景减除+斑点检测。**
> 关键补充：**反射波纹傅里叶频谱法**（陈雨琦等 2021，FFT 幅值和 + SVM，准确率 **99.24%**）——**完全不需要检测到鱼**，专为"高密度 + 水面不稳 + 光线暗"设计。**这让 L0 在鱼群密集、看不清个体时也能输出可靠的活跃度**，是 L0 层最有价值的补充。

```
┌─ 第 0 层（Day 0，零数据，当天可跑）────────────────────────
│  A 组 · 颗粒通道（相机固定时）
│   · 背景建模（cv2.createBackgroundSubtractorMOG2 / KNN）→ 前景掩膜
│   · 颗粒：ROI 内形态学 + cv2.SimpleBlobDetector（面积/圆度/凸性过滤）
│   · ★ 两步法：先减去动物检测掩码 → 再限定投饵板 ROI 内检测（ShrimpFarming 验证）
│   → 输出：颗粒数-时间曲线（核心指标！）
│
│  B 组 · 活跃度通道（鱼体无关型，不需要检测器）
│   · Farneback 稠密光流 → 平均光流幅值
│   · 帧差能量（CVFAI 骨架，含重叠系数校正 + 反光掩膜）
│   · ★ 反射波纹傅里叶频谱（FFT 幅值和）——高密度/看不清鱼时的最优解
│   · GLCM 纹理统计
│   → 输出：活跃度曲线、摄食起止时刻（阈值 + 持续性判据，见下）
│   ✅ 零训练、确定性、可解释、当天出结果
│
├─ 第 1 层（Day 0，零数据，语义辅助）──────────────────────
│  YOLOE 开放词汇检测：文本提示 "fish" / "feed pellet"
│  ✅ 无需训练，共用 Ultralytics API
│  ❌ 小颗粒召回率低，只作参考/预标注，不作最终指标来源
│
└─ 第 2 层（Day 1–2，30–80 帧标注后）────────────────────
    YOLO11m 微调（鱼）+ YOLO11s/m 微调（颗粒）
    ★ 解锁鱼体依赖型指标：FIFFB、ANND/MDC、热力图、
      以及最重要的「投喂区鱼数占比 / 相对偏好系数 RP」
    ✅ 这才是"能横向比较"的正式方案
```

#### 摄食起止时刻：用信号阈值划定，不训练时序模型

> **（v2 新增，来自 PM + 2026 年 EfficientFeedingNet 的双重印证）**
> 不要训练模型去预测摄食区间。用光流/帧差能量信号 + 持续性判据直接划定（PM 报告 D2/D3 给出判据）：
> - **起始**：信号 `> μ_base + 3σ_base` 且**持续 ≥ 1 s**
> - **结束**：信号回落 `< μ_base + 2σ_base` 且**持续 ≥ 3 s**
>
> 其中 `μ_base / σ_base` 取自**投喂前基线期**——**这就是"必须要有投喂前空镜头"的原因**（见 §6 新问题 5）。
> ✅ 零训练、可解释、阈值可调，天然适配 L0 层。
> 佐证：EfficientFeedingNet（*Animals* 2026, 16(5)）用帧对光流 → V-Value 信号自动划定摄食区间达 96.53%，且其自动标注**比人工标注数据集高 13.13–18.46 个百分点**——说明**人工主观标注本身就是噪声源**。

#### 明确回答用户的两个问法

| 问法 | 回答 |
|---|---|
| 「用通用 YOLO 权重 + 规则法能不能跑出可用结果？」 | **鱼检测：不能**（COCO 无该类）。**颗粒计数：能**——但靠的是**规则法（背景减除+斑点检测）**，不是 YOLO。规则法在"固定相机 + 固定 ROI"下对颗粒计数**效果可能比深度学习还稳**。 |
| 「还是要用户先标注几十帧微调？」 | **是的，这是必经之路，但成本很低。** 建议 **30–80 帧**（从 3–5 段视频各抽 10–20 帧，覆盖：投喂前/投喂中峰值/接近吃完/吃完）。用 Label Studio + 视频插值，实际标注耗时约 **1–2 小时**。 |

#### ⚠️ 一条必须写死的指标设计纪律：活跃度与聚集度不得合成

> **（v2 新增，PM 修正意见，我完全接受）**
> 我在初版里把"速度 + 密度 + 光流幅值"笼统称"活跃度"，**这是错的**。三者测的是**两个相反的构念**：
>
> | 指标族 | 含义 | 回答的问题 | 诱食性强时的方向 |
> |---|---|---|---|
> | **活跃度 Activity** | 光流幅值 / 帧差能量 / 平均速度 | 动得多猛 | **上升** ↑ |
> | **聚集度 Aggregation** | ANND / MDC / 热力图密度 / 投喂区鱼数占比 | 聚得多紧 | **ANND 下降** ↓（距离变近） |
>
> **诱食性强的表现恰恰是"活跃度升 + ANND 降"这个相反方向的组合**——这本身就是最强的判别信号。**合成一个"活跃度综合分"会把这个信号抹平**，且用户无法与文献对照。
>
> **工程约束：`metrics/activity.py` 与 `metrics/aggregation.py` 必须保持两个独立模块，`aggregator.py` 不得把二者合成为单一标量。**

#### 指标分级解锁表（L0 / L1 / L2）

> **一句话原则：L0 靠"不看鱼"的全局特征，L1 靠"看得见鱼但不需要跟踪稳"的几何特征，L2 才碰个体跟踪。**

| 阶段 | 解锁的指标族 | 具体指标 | 产出 |
|---|---|---|---|
| **L0（零数据）** | **鱼体无关型**（不需要检测器） | 帧差能量（CVFAI，含重叠系数校正）、光流幅值、**反射波纹傅里叶频谱**、GLCM 纹理；颗粒斑点计数 | 颗粒衰减曲线、活跃度曲线、响应潜伏期、摄食起止时刻 |
| **L1（30–80 帧）** | 上述全部 + **鱼体依赖型几何特征**（只需检测框，**不依赖 ID 稳定**） | **投喂区鱼数占比 P_fz / 相对偏好系数 RP**（★P0 主指标）、FIFFB（Delaunay 平均周长）、ANND/MDC、热力图密度、混合熵 H = H_v/H_θ | 聚集度曲线、集鱼率、**RP（诱食性主指标在此解锁）** |
| **L2（300+ 帧）** | 上述全部 + **个体级**（必须附 ID 切换率质量分） | 游速 BL/s、停留时长、首次到访时间、抢食事件计数 | 个体行为指标 |

**四个低成本补充指标（均有文献校验，进 `metrics/` 扩展位）**

| 指标 | 计算成本 | 文献校验 | 工程要点 |
|---|---|---|---|
| **CVFAI** | 极低，纯 OpenCV | 与人工评分 **r=0.9195**（Liu et al. 2014） | 含**重叠系数校正**——正好治 §4.3 难点 #2 的鱼体遮挡低估问题 |
| **FIFFB** | 低 | 与专家评分 **r=0.945**（Zhou et al. 2017） | 质心**直接取检测框中心，不必做实例分割**——**聚集度里校验最强的单项，强烈建议实现** |
| **混合熵 H = H_v / H_θ** | 低，LK 光流即可 | 摄食识别 **94.17%**（黄志涛等 2021） | 摄食期速度分布收敛（H_v↓）、转角差异增大（H_θ↑），比值变化显著 |
| **反射波纹傅里叶频谱** | 低，**完全不需要检测鱼** | **99.24%**（陈雨琦等 2021） | 专为"高密度 + 水面不稳 + 光线暗"设计——**L0 层看不清鱼时的最优解** |

> **★ 提为 P0 的指标：投喂区鱼数占比 / 相对偏好系数 RP**
> 定义 `RP = mean(投喂区鱼数) / 投喂前基线期同区平均鱼数`。
> **为什么它比"速度"强**：速度依赖 ID 稳定跟踪（ID 切换是我自己都承认的主要错误源）；**RP 只需要每帧的检测框，跟踪挂了也不影响**。在 L1 阶段就能稳定产出，且**直接回答用户"哪种料更诱食"**。
> 文献出处：虹鳟诱食剂台架（Nikiforov-Nishikin et al. 2023），实验组 122.44 vs 对照组 84.18；对应经典"集鱼率 =（诱食区尾数/全鱼数）×100%"（迷宫法，桥本芳郎）。

### 3.5 渐进路线（数据 / 算力 / 产出）

| 阶段 | 标注数据量 | 训练算力（RTX 3060 Ti 8GB） | 预期效果 | 说明 |
|---|---|---|---|---|
| **L0 冷启动** | **0 帧** | 0 | 颗粒衰减曲线 ✅ / 活跃度曲线 ✅ / 鱼数 ❌（无检测） | 规则法兜底，当天可用 |

```
Brackish / OzFish / Roboflow Fish（公开，数千张）
        ↓ 预训练（本机 1–2 小时）
   fish_base.pt
        ↓ 微调（用户 30–80 帧，10–20 分钟）
   fish_user.pt  ← 实际部署用这个
```
这样即使只有 30 帧自有数据，也能获得远好于从零训练的效果。

#### 一个容易被误解的技术点

> **YOLO 会把输入统一 resize 到 `imgsz`（默认 640）后再推理。**
> 所以 **1080p 与 720p 的推理耗时差异只有 10–20%**（差异在视频解码与 resize 上），**不是 2.25 倍**。
> 真正影响吞吐量的是：**抽帧率** 和 **是否开 SAHI 切片**。

#### ⚠️ 性能预估（v2 修订：改为变间隔抽帧，帧数下降一个量级）

> **（v2 修订）初版我按固定 5 FPS 估算，这是错的。** ShrimpFarming 验证了**变间隔采样协议**（前 2 min 每 4 s、2–4 min 每 8 s、4–20 min 每 1 min），理由是"摄食响应集中在投喂后早期"，后期只需稀疏采样即可描出衰减尾巴。
> **`ingest.py` 必须支持变间隔抽帧，默认配置建议：**
>
> | 时间窗 | 采样间隔 | 帧数 |
> |---|---|---|
> | 投喂前基线 30–60 s | 每 2 s | ~25（5 min 视频） |
> | 0–2 min | 每 2 s | 60 |
> | 2–5 min | 每 5 s | 36 |
> | 5–20 min | 每 15 s | 60 |
> | **合计（20 min 视频）** | | **≈ 156 帧** |
>
> 对比固定 5 FPS 的 6,000 帧 —— **减少约 40 倍**（ShrimpFarming 原协议更激进，仅 61 帧，约 100 倍）。

**按"20 分钟视频 → 156 帧"重算：**

| 配置 | 单帧耗时（估） | 不开 SAHI | 开 SAHI（2×2=4 片，约 4× 成本） |
|---|---|---|---|
| **YOLO11m + RTX 3060 Ti（推荐）** | ~6 ms | **~1 秒** | **~4 秒** ✅ |
| YOLO11n + RTX 3060 Ti | ~3 ms | ~0.5 秒 | ~2 秒 |
| YOLO26n + RTX 3060 Ti | ~3 ms | ~0.5 秒 | ~2 秒 |
| **YOLO11m + CPU（11 代 i7，ONNX）** | ~183 ms | ~29 秒 | **~2 分钟** ✅ |
| YOLO11n + CPU（ONNX） | ~50 ms | ~8 秒 | ~32 秒 |
| 传统 CV 规则法 + CPU | ~15 ms | ~2 秒 | 不适用 |

> **结论（v2）：算力彻底不是瓶颈。** 推荐配置下（3060Ti + YOLO11m + SAHI）**20 分钟视频约 4 秒跑完**；即使 CPU-only 也在 2 分钟内。
> **这意味着我们完全用得起更贵的配置**：可以放心开 SAHI、提高 `imgsz` 到 1280、做多尺度 TTA、跑 3 个模型投票——**把省下来的算力全部换成检测精度，这才是本项目真正的瓶颈所在**。

#### ⭐ 用户本机无 GPU 时的降级方案（三层）

1. **首选：装 CUDA 版 PyTorch，用上现有的 3060 Ti。**（用户机器本来就有，只是装错了包——这是零成本收益）
2. **次选：ONNX Runtime + CPU。**
   `model.export(format="onnx")` → 用 `onnxruntime` 推理。YOLO11n 在 11 代 i7 上约 20 FPS @640。
   注意：用户已装 `onnxruntime 1.20.1`（CPU 版）。
3. **兜底：INT8 量化 / OpenVINO。**
   Ultralytics 支持 `format="openvino"`，Intel CPU 上可再提速 1.5–2×。用户机器是 Intel，这条路有效。
4. **编码层优化：** 用 `opencv-python-headless`（48MB，比 `opencv-python` 小且无 GUI 依赖）+ `cv2.CAP_FFMPEG` 硬解。

> **算力不是本项目的瓶颈。** 真正的瓶颈是**标注数据**和**粒径/反光带来的检测精度**。

### 4.1 推荐技术栈与理由

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 | **Python 3.11** | 用户已装 3.11；PyTorch cu126 / Ultralytics / OpenCV 5.0 均支持 |
| 深度学习 | **PyTorch 2.x (cu126)** + **Ultralytics YOLO11m** | 生态最成熟；训练/推理/导出一条命令；社区教程最多，用户二次开发成本最低 |

| 小目标 | **SAHI (MIT)** | 饲料颗粒 8–30 px，原生 640 输入必漏检，切片推理是刚需 |
| 传统 CV 兜底 | **OpenCV** 背景减除 + 斑点检测 + 光流 | 冷启动零训练方案；也是反光/浑浊时的补充信号 |
| UI | **Gradio** | 视频上传/预览/进度条开箱即用，单机 Web 应用最省事 |
| 指标与导出 | **pandas + matplotlib** → CSV / PNG / JSON | 用户要"横向比较"，CSV 是刚需；图表用于汇报 |
| 标注 | **Label Studio**（`pip` 安装） | 免 Docker；支持视频插值标注与 YOLO/COCO 导出 |

**为什么不用别的组合？**
- ❌ **不引入 MMDetection/MMAction2**：Ultralytics 已覆盖检测/分割/姿态/跟踪，再引一套 OpenMMLab 栈会 doubling 环境复杂度，收益为负。
- ❌ **不引入 VIAME 作为底座**：C++ 重型、License 不标准、二次开发门槛高。它适合海洋科考队，不适合"用户装个软件跑视频"。
- ✅ **Gradio 优于 Streamlit**：本任务是"上传视频 → 等几分钟 → 看结果"，Gradio 的 `gr.Progress` + 队列机制对长任务更友好。

### 4.2 视频处理管线（六段）

```
[1] 输入与预处理
    视频解码(cv2) → 视频元信息(时长/FPS/分辨率) → ROI 标定(人工/自动) 
    → 抽帧(★变间隔，默认 0–2min/2s、2–5min/5s、5–20min/15s)
    → [可选] 水体增强(去雾/CLAHE/白平衡)
                    ↓
[2] 检测（双通道并行）
    通道A 鱼：YOLO11m/YOLO26m (微调权重) + [可选]SAHI
    通道B 颗粒：YOLO11s/m (微调权重) + SAHI(必开)
    通道C 兜底：MOG2 背景减除 + Blob 检测（当模型置信度低时融合）
    ★ 两步法：颗粒检测前先减去动物掩码 → 再限定投饵板 ROI
                    ↓
[3] 跟踪与后处理
    BoT-SORT/ByteTrack(鱼) → 轨迹 → 速度/加速度/轨迹长度
    颗粒：轻量关联(匈牙利匹配, 因颗粒多且生命周期短，不做完整 MOT)
    ★ 输出 ID 切换率作为质量分（所有个体级指标必须附带）
                    ↓
[4] 时序指标聚合（★ activity 与 aggregation 严格分离，不得合成）
    · A 组 颗粒：N(t) → 拟合衰减 → ★RR(固定窗残留率, 主) + T50(主) / T90(辅)
                 ★ N₀ 双轨校验：视觉峰值 vs 元数据推算，差>20% 告警
    · B1 活跃度：光流幅值、帧差能量(CVFAI)、傅里叶频谱、速度
    · B2 聚集度：ANND/MDC、FIFFB、热力图密度、★投喂区鱼数占比 P_fz / RP（P0）
    · 摄食起止时刻：信号阈值 + 持续性判据（不训练模型）
                    ↓
[5] 可视化输出
    标注视频(mp4) + 热力图 + 曲线图(颗粒衰减/活跃度) 
                    ↓
[6] 导出
    metrics.csv(逐帧) + summary.json(汇总指标) + run_config.yaml(参数留档) + charts/*.png
```

### 4.3 关键工程难点与对策

| # | 难点 | 对策 |
|---|---|---|
| 1 | **小目标漏检**（饲料颗粒 8–30 px） | ① **SAHI 切片推理**（slice 512×512 / overlap 0.2）；② 提高 `imgsz` 到 960–1280（GPU 显存够）；③ 训练时加 P2 小目标检测层（参考 YOLOv5s-CAGSDL 论文的"tiny target detection layer"思路）；④ 单帧多尺度 TTA（离线场景可接受） |
| 2 | **鱼体重叠遮挡**（密集鱼群） | ① **不追求"精确计数每条鱼"**——这是死路，改为**密度代理指标**：ROI 内检测框总面积占比、凸包面积、热力图强度；② 只对**能稳定跟踪 ≥N 帧**的轨迹做个体级统计，其余归入"群体密度"；③ 用 `sv.DetectionsSmoother` 平滑 ID 抖动 |
| 3 | **颗粒 vs 粪便 / 气泡 / 虾体 / 阴影误判** | ① **★ 两步法（ShrimpFarming 验证有效）**：先减去已分割的**动物掩码**，再限定**投饵板 ROI 掩码**内检测——单靠 HSV 色域分割会在光照变化时失效并误检动物体与阴影；② **形态过滤**：面积区间、圆度（4πA/P²）、凸性、长宽比；③ **轨迹过滤**：饲料颗粒**下沉速度稳定且单向**，气泡**上浮**、粪便**形态不规则且不下沉**——用连续帧位移向量方向判定；④ **时序一致性**：真颗粒在投喂前不存在、投喂后单调减少 |
| 4 | **水面反光 / 波浪** | ① 相机固定时用**背景建模**（MOG2 history=500）把静态反光吸收进背景；② **ROI 排除**高反光区域（UI 上用多边形工具标出）；③ 用**时间中值滤波**：对连续 N 帧取中值图作参考帧；④ **偏振镜 CPL**（硬件建议，成本极低）；⑤ ⚠️ **不要建议用户加装亚克力/玻璃罩**——ShrimpFarming 实测：亚克力表面瑕疵导致持续失焦模糊，拉开距离后反光噪声又回来，**方案已被废弃**，最终改为"把投饵板置于反光最小区域" |
| 5 | **视频时长与处理耗时** | ① **★ 变间隔抽帧**（默认 0–2min/2s、2–5min/5s、5–20min/15s；20 min 视频仅 ~156 帧，比固定 5 FPS 少 40 倍）；② **ROI 裁剪后推理**（只处理养殖区域）；③ 批量任务用 `stream=True` 生成器 + 进度回调；④ GPU 批量推理（`batch=8`）。**省下的算力应全部投向精度**（更大 imgsz、开 SAHI、多尺度 TTA） |
| 6 | **结果可复现** | ① **所有参数写进 `run_config.yaml`**（模型路径、置信度、IoU、ROI 多边形、抽帧率、SAHI 参数、颗粒过滤阈值、随机种子）；② 输出时**随结果一起导出**；③ 汇总指标 JSON 里记录**软件版本 + 权重文件 md5**；④ 提供"导入配置复跑"功能——**这对饲料横向比较是刚需**（不同饲料必须用同一套参数跑） |
| 7 | **浑浊水体** | ① CLAHE 自适应直方图均衡；② 暗通道先验去雾（OpenCV 可轻量实现，思路来自 VIAME）；③ 训练数据加浑浊增强 |
| 8 | **AGPL 合规**（非技术但重要） | 见 §2.1 风险提示。**第一版就需在 UI 或 LICENSE 中声明**，并让用户确认使用范围 |
| 🔴 **9** | **N₀ 被系统性低估 → 归一化曲线偏移，且组间偏差不一致**（PM 发现，本项目最隐蔽的陷阱） | **问题**：t≈0 时颗粒最密、重叠最严重 → 检测器召回率恰恰最低 → N₀ 低估 → 整条归一化曲线系统性偏移。**更糟的是偏差在组间不一致**：诱食性强的料被吃得快、分散快、重叠轻、召回高；诱食性弱的料堆积久、重叠重、召回低 → **人为放大组间差异，得出错误结论**。<br>**对策（必须工程化）**：① N₀ 取**投喂后早期窗口的平滑最大值**，而非单帧 argmax；② **双轨校验**：`N₀_meta = 投喂量(g) ÷ 单颗均重(mg)`，**两个 N₀ 都算都输出**，差距 **>20% 即在报告中告警**（这是发现漏检最省事的手段）；③ 分组比较时**必须锁定同一套 N₀ 口径**（由 `run_config.yaml` 兜住） |
| 🔴 **10** | **"被吃掉"与"沉底/漂出"在纯 2D 视频里本质不可分**（PM 编号 A14，本项目最大的技术陷阱） | **不要用"颗粒数=0"作为"吃完"的主口径。** 改为 **RR（固定观察窗末残留率）+ T50 双轨**：<br>· **主指标 RR** = 固定观察窗（建议 5 min；文献口径：虹鳟台架 5 min、AFFIA3K 投喂窗 3 min）结束时 `N_p / N₀ × 100%`——**不依赖"清零"这个不稳定事件，跨组可比性最好**<br>· **速度指标 T50（主）+ T90（辅）**——T50 位于曲线最陡处，信噪比最高<br>· **T95/T100 降为参考值**，必须与非摄食损失颗粒数**一起展示**，**不许单独作为"吃完时间"对外**<br>· **UI 上把阈值做成可配置，报告里写明用了哪个阈值**（不同阈值不可直接比较）<br>· ⚠️ **若用户用沉性料，此风险致命**，须先确认饲料浮沉性（见 §6 问题 6） |
| 🟠 **11** | **摄食起止时刻的划定** | **不训练时序模型。** 用光流/帧差能量信号 + 持续性判据划定：**起始** `> μ_base+3σ_base` 且持续 ≥1 s；**结束** 回落 `< μ_base+2σ_base` 且持续 ≥3 s（`μ_base/σ_base` 取自投喂前基线）。零训练、可解释、阈值可调 |
| 🟠 **12** | **可见密度决定哪些指标可用**（PM 提供矩阵） | **做成产品的能力开关**，按密度自动降级（详见 §6 后的密度—指标可用性矩阵）。高密度下**依赖鱼体检测的所有指标一律标低置信并降权**，主输出切到鱼体无关型（帧差/光流/傅里叶/GLCM） |

### 4.3.1 密度—指标可用性矩阵（产品的能力开关）

| 可见密度 | 可输出 | 必须关闭 / 强制标低置信 |
|---|---|---|
| **低**（≤10–15 尾，无严重遮挡） | A 组全部 + B 组全部（活跃度 & 聚集度）+ **C 组个体指标** | — |
| **中**（15–40 尾，偶发遮挡） | A 组全部 + B 组（**鱼体无关型优先**） | **C 组个体指标关闭**（游速 BL/s、停留时长、咬食次数） |
| **高**（>40 尾 / 严重遮挡 / 浑浊） | **A 组 + B 组的鱼体无关型**（帧差 / 光流 / 傅里叶 / GLCM） | 投喂区鱼数占比、ANND、FIFFB 等**依赖鱼体检测的指标一律标低置信**；C 组全关。**此时主输出应为颗粒曲线（A 组）而非行为曲线（B 组）** |

> **对抢食型 vs 温和型鱼种的补充**：黄带拟鲹、石斑等抢食激烈、水花大 → 水花/光流是**有效信号**；温和摄食的鱼水花少 → **光流信号弱，活跃度指标灵敏度大幅下降**，此时**更要依赖颗粒曲线（A 组）而非行为曲线（B 组）**。

### 4.4 指标契约与降级架构（v3 新增，衔接 PM 的 `docs/04`）

PM 已交付《指标输入契约》（`docs/04-metrics-input-contract.md`），定义了 A/B1/B2/C/D 五组共 40+ 个指标的**输入 → 输出 → 质量分 → 失效条件**，以及 13 个全局质量信号、26 个阈值常量、9 个必测单测场景。**本节只记录架构侧的承接决策，指标定义以 `docs/04` 为准。**

#### 决策 1：用 `MetricValue` 数据结构把"不得用 0 冒充"变成结构性强制

契约里散落着多条同义禁令（"不得用 0 填充"、"严禁默认为 0"、"严禁 NaN 冒充"、"失效时显式列出原因"）。**靠文档约定约束不住，我把它做成类型约束：**

```python
@dataclass(frozen=True)
class MetricValue:
    metric_id: str
    value: float | None                          # None = 不可用/删失，绝不是 0
    unit: str | None
    status: Literal['ok','degraded','unavailable','censored']
    reason: str | None                           # status != 'ok' 时必填
    flags: tuple[str, ...]                       # 可为空
    quality: dict[str, float]                    # 引用 13 个 Q_* 信号
    unit_scale: Literal['px','mm','BL','none']   # 处理 Q_calib 缺失的三级降级

    def __post_init__(self):                     # ★ 构造期即强制，事后无法绕过
        if self.status != 'ok' and not self.reason:
            raise ValueError("非 ok 状态必须给出 reason")
        if self.status in ('unavailable','censored') and self.value is not None:
            raise ValueError("不可用/删失时 value 必须为 None，严禁 0/NaN 冒充")
        self._check_unit_scale()                 # ← 见下方量纲依赖链

    def _check_unit_scale(self):
        """量纲依赖链（v4 修正：BL 与 mm 的依赖不同，不可合并校验）"""
        q = self.quality
        if self.unit_scale == 'mm' and q.get('Q_calib') is not True:
            raise ValueError("未标定（Q_calib=False）不得输出 mm 量纲")
        if self.unit_scale == 'BL':
            if q.get('Q_bodylen') is not True:
                raise ValueError("体长不可得（Q_bodylen=False）不得输出 BL 量纲")
            # ★ 关键：BL 是尺度无关量，走不同路径
            #   bodylen_source == 'measured_px' → px/s ÷ px 直接得 BL/s，不需要 Q_calib
            #   bodylen_source == 'meta_mm'     → 速度须先转到 mm/s，因此仍需要 Q_calib
            src = q.get('bodylen_source')
            if src == 'meta_mm' and q.get('Q_calib') is not True:
                raise ValueError("体长来自元数据(mm)时，BL 换算依赖 Q_calib")
            if src not in ('meta_mm', 'measured_px'):
                raise ValueError("bodylen_source 必须是 'meta_mm' 或 'measured_px'")
```

> **（v4 修正，PM 指出）** 我原写法 `unit_scale in ('mm','BL') and Q_calib is not True` 是错的：**`Q_calib` 只解决 px→mm，而 px→BL 还需要体长**，两者依赖不同。
> 修正后额外引入 **`Q_bodylen`**（体长是否可得）与 **`bodylen_source`**（`meta_mm` / `measured_px`）两个质量字段。
> **附带发现**：**BL 是尺度无关量**——若体长能在画面内实测（`measured_px`），则 `px/s ÷ px` 直接得 BL/s，**无需标定**。这意味着**未标定的视频仍可能输出 BL/s**，只是精度低于元数据路径。这条对没有标定板的用户有价值。

> **收益**：契约的 4 条设计原则从"工程师要记得遵守"变成"**写错了构造不出来**"。这是本节最重要的一条决策。

#### 决策 2：自动推断的分类只能降级，永远不能关闭（回答契约 §8 未决项 #4）

PM 担心摄食烈度档（VIGOROUS/GENTLE）的自动判据不可靠会误关指标。**我的处理不是"只作提示"，而是升格为一条通用架构规则：**

> **任何自动推断的分类（烈度档、机位类型、鱼种等）只被允许追加 ⚠️ 标记，绝不允许触发 ❌ 关闭。**
> 只有两类东西有权关闭指标：**① 实测质量信号（13 个 Q_*）；② 用户显式提供的元数据。**

具体到烈度档：`UNKNOWN` 时按**更保守的 GENTLE 分支处理**（追加 `low_sensitivity` 标记），但**不关闭任何指标**。UI 上做成**必填下拉框 + 自动建议值预填**，不是纯提示——纯提示用户一定会跳过。

#### 决策 3：颗粒关联算法 + 与变间隔抽帧的冲突（回答契约 §8 未决项 #3，**这条是我自己引入的问题**）

**不用匈牙利匹配**（那是为有外观/运动模型的 MOT 设计的，对数百个近静态小目标过重且无收益）。**改用带物理约束的时空最近邻关联：**

```
关联可行条件：max_displacement = v_sink_max × Δt  <  association_radius
```

**⚠️ 但这里有一个我在 v2 引入的隐性冲突，必须修掉：** 变间隔抽帧在尾段是 15 s 间隔，**15 秒的帧间空档下颗粒早已沉出视野或被吃掉，任何关联算法都无意义**——即 **A14（非摄食损失率）在稀疏段不可计算**，而 A14 恰恰是 T90/T100 的校正依据。

**解决方案：非对称采样（asymmetric sampling）**

| 时段 | 间隔 | 帧数 | 理由 |
|---|---|---|---|
| 基线 `[-60s, 0)` | 2 s | 30 | 基线统计 |
| **动态早期 `[0, 60s]`** | **1 s** | 60 | 衰减曲线最陡段 + **A14 关联在此窗口内才成立** |
| 尾段 `[60s, 300s]` | 10 s | 24 | 只需描出尾巴算 RR |
| **合计** | | **≈ 114 帧** | 仍比固定 5 FPS（1800 帧）少 **16 倍** |

> 关键：**A14 只在密集窗口内计算**，并显式记录 `a14_window_s`；若观察窗长于该窗口，标记 `partial_window=True`，**且 T90/T100 不得声称"已全程校正沉降损失"**。
> 若 `pellet_type == 'sinking'`（沉降损失最关键的场景），**建议用户额外提供一段 60 s 的高帧率视频专供 A14 校正**——因为算力根本不是瓶颈，这段成本几乎为零。

**（v4 追加）`v_sink_max` 禁止硬编码 → 引入"预标定"步骤解决自举问题**

PM 指出 `v_sink_max` 不同饲料差异极大（浮性/缓沉/沉性、粒径、水温均影响），**1 s 间隔对沉性料可能仍不够，且会静默失效**（关联不上、程序不报错，A14 悄悄变成 unknown）。同意，**`v_sink_max` 禁止硬编码、config 不给默认值**（给了就会被当成真值用）。

但这条带来一个自举问题：**`v_sink_max` 未知 → `Δt_max = association_radius / v_sink_max` 未知 → 无法决定采样间隔。** 因此管线必须增加一个前置步骤：

```
scripts/00_calibrate_pellet_dynamics.py      # ★ 新增，跑在主流程之前
  输入：无鱼纯饲料视频（同名素材，一物三用，见下）
  输出：v_sink_max（竖直位移/时间的 95 分位，非最大值，防异常值）
        association_radius（2–3 倍粒径）
        px_per_mm（若画面内有标定参照物）
        Δt_early_recommended = association_radius / v_sink_max × 安全系数(0.5)
  写入：configs/calibration/<feed_id>.yaml，供后续正式运行引用
```

> **硬性约束**：若 `Δt_max < 当前采样间隔` → A14 **显式标记 `partial_window` 并声明不可用**，**不得崩溃、也不得静默跳过**。
> **待回验项**：拿到 `v_sink_max` 实测值后需确认早期 1 s 间隔是否足够（契约 §8 #7）。

> **📌 「无鱼纯饲料视频」一物三用——建议向用户只要"一段"而不是"三段"**（PM 提出，采纳）：
> ① 颗粒检测器的纯净正样本；② **A14 非摄食损失的标定基准**（无鱼时颗粒减少**只可能**是沉降/漂出，这是唯一能纯净测量非摄食损失的条件）；③ **`v_sink_max` / `association_radius` 标定源**。
> **配合成本降三分之二，且三段数据采集条件天然一致。**
> ⚠️ `v_sink_max` **只能用无鱼视频标定**——有鱼视频测出的是"摄食+沉降"混合速度，会让关联约束失效且极难排查。

#### 决策 4：输出不得重采样到 1 Hz（**对契约 §3 采样率约定的一处修正**）

契约写"对外统一重采样到 1 Hz 输出"。**这一条我不同意，需要改。**
非对称采样下尾段真实间隔是 10 s，**把它重采样到 1 Hz 等于凭空插值出 9 个不存在的观测点**——后续任何人拿这份 CSV 算 AUC、算积分、算斜率，都会得到与真实数据不同的结果，而且**看不出自己算错了**。

**改为双层输出：**
- `metrics_timeseries.csv` —— **保留原生不规则时间戳**（`t_seconds` 列，间隔不等），**这是唯一可信源**；不可用点为真正的空值。**必须包含 `dt_s` 列**（距上一采样的真实间隔，PM 补充，采纳）——**这是最便宜的防呆**：没有它，用户在 Excel 里对不规则时间戳做积分时会默认等间隔而算错，且同样看不出自己错了。
- `metrics_timeseries_1hz.csv` —— 重采样版，**默认不导出**（`export_1hz_timeseries: false`），导出时每行带 `interpolated` + `source_interval_s`，文件头注明"插值数据，不可用于积分/统计"。

**（v4 追加，PM 补充）真正的规则不是"禁止重采样"，而是"积分/微分/拟合必须在原生序列上算"**

即使把间隔压到 5 s 甚至 1 s，只要存在重采样环节，拟合仍可能被错误地做到重采样序列上。因此写成显式约束：

> **A5 v(t)、A6 v_max、A12 (k,τ)、A13 AUC₆₀、D6 FA_AUC、D7 k_rise、D8 k_fall、B2-10 τ_disp 一律在原生序列上计算，积分用 `np.trapz(y, t)`（基于真实 dt 的梯形法），不得用 `sum(y)/fps`。**

**（v4 追加）两种插值要区分，别因噎废食**

| 类型 | 判定 | 处理 |
|---|---|---|
| **合法且应当做** | 在**已有观测之间**插值，用于定位**事件的精确时刻**——不制造观测 | **A8/A9/A10 求 T50/T90/T100 穿越点的线性插值必须保留**，去掉会白白损失时间分辨率 |
| **非法** | 制造**不存在的观测点**，并让下游当真实数据做积分/统计 | 10 s 序列重采样成 1 Hz |

> 附带结论：**不采纳"把最大间隔压到 5 s"这个替代方案**（PM 反对，我同意）。它没有解决真正的问题——假点只是从 9 个变成 4 个，仍然是假点；真正的修复是「原生为唯一可信源 + `interpolated` 标记」。**不为非修复方案付帧数成本。**
> 另外，**非均匀采样对积分其实有利**（早期密/曲线陡，尾段疏/曲线平 = 自适应积分），比等间隔更准，**不要为了"整齐"压缩尾段**。
> 图表层：**默认画原生序列**；要画平滑线，须以原生点为 marker 叠加，不得只画插值线。

##### ⚠️ 关于 `trustworthy` 列的取舍判断（PM 请我评估风险）

PM 提议增加 `trustworthy` 布尔列，并已自行做了关键的风险控制——**不阻止输出、不自动过滤、`summary.json` 保留完整 flags 供专家复核**。这个自我约束是对的，我完全同意"绝不做成自动过滤"。

**但我认为 `trustworthy` 这个名字有实质风险，建议改掉。**

> **风险不在"过滤"，而在"过度承诺"。**
> `trustworthy == True` 的实际含义是「**未检测到已知缺陷**」，但用户会读成「**这个数是准的**」。这两者差别很大——**没有检测到的缺陷 ≠ 已验证的准确度**。我们没有任何真值对照机制，没有任何指标被"验证"过；用一个名为 `trustworthy` 的布尔值，等于对用户做了一个我们无法兑现的承诺。
> 而且这类误读**同样不可察觉**：用户信任了不该信任的数，不会有任何报错。

**建议改为三列组合（替代单个布尔）：**

| 列 | 内容 | 作用 |
|---|---|---|
| `blocking_flags` | 命中阻断清单的 flag，**分号分隔的字符串**（可为空） | 用户筛"空值"即得原 `trustworthy=True` 的效果；**但理由和结论在同一行，筛选无法把二者分开** |
| `blocking_flag_count` | 整数 | 排序/统计用；**数字比布尔更难被过度信任** |
| `flags` | 全部 flag（含非阻断） | 专家复核 |

**设计原则：筛选辅助列必须与其判定依据相邻。** 这样即使用户只按 `blocking_flags == ""` 过滤，理由也始终在视野内。这比一个孤零零的 `trustworthy` 布尔安全得多。

> **（v5，PM 指出我方案里的一个 bug 并给出修法，采纳）**
> **🔴 我的 `blocking_flag_count` 有排序陷阱。** 若它只统计内容 flag，则 `status='unavailable'` 的指标计数为 **0**——**排序时会排在最前面，伪装成"最干净"的那批**。这与我们一路禁止的"用 0 冒充空值"是同一个坑，只是换了个地方。**PM 的修法**：
>
> > **`blocking_flags` 在 `status != 'ok'` 时必须额外包含一项 `status:<值>` 伪 flag**（如 `status:degraded`、`status:censored`、`status:unavailable`）。
>
> 这一个改动同时解决三件事：
> 1. **单一列即可筛选**——`blocking_flags == ""` 等价于"ok 且无阻断"，用户不必再另看 `status` 列；
> 2. **排序陷阱消失**——非 ok 的计数恒 ≥ 1，不可能排到最前；
> 3. **`uncalibrated` 类漏筛自动解决**——B1-3 傅里叶的 `calibrated=False` 是非阻断 flag，但它必然伴随 `status='degraded'`，于是经伪 flag 进入 `blocking_flags` 被正确拦截。

**阻断清单（7 项，非用户可配）**：`contains_non_feeding_loss` / `denominator_suspect` / `sedimentation_risk_unassessed` / `counting_unstable` / `unstable_baseline` / `low_conf` / **`degenerate`**。
> - 第 3 项 `sedimentation_risk_unassessed`：PM 顺着"元规则"自查补的——`pellet_type == UNKNOWN` 时**不关闭、不降级**（UNKNOWN 无权关闭），但必须打此标记。
> - 第 7 项 `degenerate`：PM 补的，几何退化（如 FIFFB 质心重复率超阈值）意味着**计算基础已被破坏**，比 `low_conf` 更该阻断。
> - **`unnormalized` 不在阻断清单内**（PM 判断，我认同）：px 口径的 ANND **在单次分析内仍有意义**，一刀切会误伤；它的问题是**不可跨视频比较**，因此改由 `compare.py` 在比较层拦截（见下）。
> - **不开放给用户配置**（契约 §8 #9）：开放后不同分析间"阻断"含义不一致，**跨批比较反而更危险**——与 `run_config` 必须锁定同理。用户若要自定义严格度，自行按 `flags` 列筛选。

##### ⭐ 我对 PM 方案的补充（v5 提出，v6 与 PM 收敛）

**① 版本化：采纳 PM 的简化建议，用单一 `metrics_spec_version`**

我原提 `blocking_flags_version` **单独**设一个版本号。PM 建议合并为单一 `metrics_spec_version`（阈值 + 阻断清单 + 指标定义共用一个版本号），**我采纳**——她的理由成立：

> ① 阻断清单与指标定义在实践中一起变（加一个 flag 几乎总是伴随某个指标定义细化）；
> ② **版本项越少越不容易被漏 bump**——本项目的核心风险就是静默失效，每多一个需人工维护的元数据项就多一处风险；
> ③ 两种不一致的补救动作相同，细分没换来不同处理。

我原本的顾虑是"报错信息希望能区分是指标定义变了还是清单变了"，**但 `compare.py` 本来就会 diff 整个 `run_config`**，所以具体差异（如 `blocking_flags: [7 项] → [8 项]`）会自动显示出来。
> **结论：单一版本号负责"闸门"，`run_config` diff 负责"诊断"。** 两者兼得，且只需维护一个版本号。

> **要求**：`metrics_spec_version`（如 `ms-v1`）写入 `run_config.yaml` 与 `metrics_summary.csv` 第 17 列，`compare.py` 校验。

**② `compare.py` 两条拒绝规则**

| 触发条件 | 行为 |
|---|---|
| 两个 run 的 `px_per_mm` 不一致 | **拒绝比较任何带 `unnormalized` 的指标**，并在对比报告中显式列出被拒绝的指标及原因（PM 提出） |
| 两个 run 的 **`metrics_spec_version`** 不一致 | **拒绝整份比较** |

> **关于"拒绝"是否过严（PM 提出，我同意她的结论）**：**拒绝更对，因为补救成本极低**——重跑一段视频在本机约 4 秒。正解是**重跑对齐**，而不是让用户带着警告继续（带着警告继续，用户大概率会忘记，然后在论文里写下错误结论）。
> **但报错信息必须把用户引向这条最低成本出路**（PM 补充，采纳）：
> > 「不可比较：run A 使用 `ms-v1`，run B 使用 `ms-v2`。请用当前版本重新分析其中一份（各约 4 秒），或单独查看各自结果。」
>
> **不要只说"版本不一致，拒绝比较"然后把用户卡住**——那会逼他去想办法绕过。

**③ 术语表要触达只读 CSV 的用户**

PM 要求 `capability_report.md` 含一节「flag 术语表」（每个 flag → 一句用户能懂的中文），**这条我完全同意——给了一堆标记却不告诉用户含义，等于没给**。
**补充**：另出一份 **`flag_glossary.csv`** 与 `metrics_summary.csv` 并列同目录。**只看 CSV 的用户（很可能有相当比例）不会去打开 .md**，术语表必须在他们的动线上。

列定义：`flag_token, 中文名, 含义, 建议动作`。

#### 决策 6：验证模式（v6 新增）—— 把工具从"能出数"变成"敢用这个数"

PM 在问卷里加了 Q21（愿不愿意做一次人工对照），并认为这是整份清单里对用户价值最高的一条。**我完全同意，并补上工程侧的落地设计。**

> **为什么它关键**：我们目前**没有任何真值对照**，所以只能承诺"未检出缺陷"，无法承诺准确度。
> **但只要用户肯做一次人工对照，情况立刻不同**——这是唯一能把"未检出缺陷"升级为"实测误差 = X"的路径。

**新增一个独立的运行模式 `validate`（不混入正式分析）：**

```
scripts/06_validate_against_groundtruth.py
  输入：一段已分析过的视频 + 人工真值表（CSV: t_seconds, pellet_count_truth[, intensity_score]）
  输出：validation_report.md + validation_pairs.csv
```

`validation_report.md` 内容：
| 项 | 说明 |
|---|---|
| 逐帧对照表 | `t / 预测值 / 人工值 / 差值` |
| **MAE / MAPE** | 颗粒计数的绝对与相对误差 |
| **有符号偏差（bias）** | ⭐ 判断我们是**系统性低估**还是随机误差——这直接对应难点 #9（N₀ 低估） |
| Bland-Altman 一致性 | 误差是否随浓度变化（小样本下比相关系数更合适） |
| 与专家强度评分的相关系数 | 若提供了 `intensity_score`（文献同类指标 r=0.92/0.94，此处给**本场景实测值**） |

> **⚠️ 三条硬性纪律（前两条我提，第三条 PM 补，我再加一个关键推论）：**
> 1. **禁止基于 <30 帧的真值自动施加任何校正系数。** 只报告偏差，由用户决定是否采信。**用小样本自动校正是典型的"兑现不了的承诺"**，正是我们一路在防的失败模式。
> 2. **人工计数必须先定义计数协议**，否则"真值"不是真值：
>    - 计入范围：质心落在 `ROI.pellet_zone` 内即计入（含部分遮挡的颗粒）
>    - 粘连颗粒：可见分界线则计 2，不可见则计 1
>    - 边缘颗粒：压线按质心判定
>    - 建议同一帧由**两人独立计数**，不一致时复核——否则评分者内变异会淹没测量本身
> 3. ⭐ **必须报告"真值自身的噪声下限"**（PM 提出）：
>    > **真值本身也有误差。** 若人工计数在密集帧上的评分者间差异就有 ±10%，那么声称"我们的 MAE = 8%"是**没有意义的**——我们无法区分自己的误差和真值本身的噪声。
>    > **只有当我们的误差显著大于评分者间差异时，"误差"这个说法才成立。**

##### 🔴 我对纪律 3 的关键补充：**误差低于噪声下限时，结论是"无法测量"，不是"误差为零"**

PM 的纪律 3 指出"要报告噪声下限"，但**没说当我们的误差低于这个下限时该报什么**。而这恰恰是本项目最容易出错的地方——**它与 `trustworthy` 是同一个陷阱换了第三次出现**：

| 场景 | 错误结论 | 正确结论 |
|---|---|---|
| 未检出 flag | ~~这个数可信~~ | 未检出已知缺陷（≠ 已验证） |
| 实测误差 < 真值噪声 | ~~**我们的误差 ≈ 0，很准**~~ | **我们的误差落在真值噪声内，本方法无法测量** |

> **两者是同一句话的两种说法：没测出来 ≠ 没有。**
> 若我们的 MAE = 8% 而评分者间差异 = ±10%，唯一诚实的输出是：
> 「**本验证无法区分模型误差与真值噪声（误差 < 噪声下限）。要获得有效结论，需提高真值质量（增加计数人数 / 采用更高分辨率人工复核 / 改用已知颗粒数的标定板）。**」
>
> **绝不能输出"MAE = 8%"这样一个看着很漂亮、实则无意义的数字**——它给用户虚假的信心，而且**同样不可察觉**。

**工程要求**：`validation_report.md` 必须把 **噪声下限与实测误差并列展示**，并在 `误差 < 噪声下限` 时**自动输出上述"无法测量"结论，同时抑制任何精度数字的高亮展示**。

> **另一条相关约束**：**不要在 <30 帧时用"减噪声"的方式去算一个"修正后的误差"**（如 `σ_model² ≈ MS(观测差) − σ_ref²`）。小样本下方差估计本身就极不稳定，且相减可能得到负值——**那会产出一个荒谬但看起来很专业的结果**。本版只做并列展示，不做代数修正。

> **补充一个容易混淆的点**：`Q_n0gap`（N₀ 检测值 vs 投喂量推算）**不是真值的替代品**。它只能捕捉**总量级的粗大误差**，无法发现**逐帧的系统性偏差**（例如稳定漏检 15% 时，`N0_meta` 与 `N0_det` 的差距会暴露，但中间各帧的比例误差它看不见）。**两者是互补关系，都要做。**

> **时机建议（PM 提出，我强烈附议）**：**务必在正式采集数据前就安排人工对照**。事后补做麻烦得多——因为真值必须在已知的、可复现的时间点上数，视频一旦归档就很难再对齐。

`ci_low` / `ci_high`（置信区间）。当前无统计推断机制，本版不实现。

### 4.5 输入侧校验：元数据交叉验证（v8 新增，PM 提出方向、我补工程质量门）

> **PM 的观察（很对）**：前 6 条硬规则全部在防"**输出**骗人"，**没有任何一条防"输入"骗人**——我们全程假设用户填写的 `RunMeta` 是正确的，而它同样可能填错，且我们没有任何校验手段。
> 用户填错 → 我们按错误的声明输出一条**干净的指标** → 用户信任 → 论文里写下错误结论。**全程无报错。**

#### 决策 7：`RunMeta` 交叉校验表（**可反查的字段全部要反查**）

| `RunMeta` 字段 | 用什么实测值反查 | 矛盾时的行为 |
|---|---|---|
| `pellet_type` | `Q_pelletloss`（经 A14） | PM 的第 7 条硬规则，见下 |
| `feed_mass_g` + `pellet_mass_mg` | `N0_det` | 已有规则 5（`Q_n0gap > 0.20`） |
| **`n_fish_total`** | `Q_vis`（平均可见鱼数） | ⭐ **仅单向**：`Q_vis > n_fish_total` → `denominator_suspect`（**这直接污染 `P_fz` 与 RP 的分母**）。**反向不告警**，见下 |
| **`body_length_mm`** | 画面内实测体长 × `px_per_mm` | 偏差过大 → `Q_bodylen` 来源可疑，BL/s 降级 |
| **`px_per_mm`** | 若画面内有已知尺寸参照物 | 自检；失败则 `Q_calib=False`，所有 mm/BL 降级 |
| **⚠️ 视频时间基准** | 实际解码帧数 / 逐帧时间戳 | **见下方专项——这是最危险的一条** |

> **（v9 修正，PM 指出）`n_fish_total` 的校验必须写成单向的。**
> **只在 `Q_vis > n_fish_total` 时告警**；**反向（`Q_vis` 远小于 `n_fish_total`）是正常现象**——遮挡、鱼游出画面、贴边都会让可见数低于总数。
> 若写成 `abs(Q_vis − n_fish_total) > X` 会**持续误报**，用户很快学会忽略这个告警，**反而失去防护作用**——**一个天天喊狼来了的告警，比没有告警更糟**（又一个"看起来在保护、实际没保护"的例子）。
>
> **另外，触发时最可能的原因不是用户数错了鱼，而是检测器重复计数/误检杂物**（同一条鱼被切成两个框、或把池底斑纹当成鱼）。因此排查引导应指向**检测器复核**，而不是让用户回去重数鱼。

> **处理原则是"覆盖 + 告知"（PM 提出，采纳）：**
> - 静默采用声明 → 可能输出错的干净结论
> - 静默采用实测 → 用户不知道自己填错了
> - **两者都要避免**

#### 🔴 我对硬规则 7 的关键修正：**覆盖声明之前，必须先过 A14 自身的质量门**

PM 的规则是：`floating` 声明 + 实测 `Q_pelletloss > 0.15` → **按实测处理**（按沉性料规则降级 T90/T100），并告知"已按实测值覆盖您的声明"。

**动作方向我完全同意，但这条规则缺一个前置条件，否则会违反原则 1。**

> **`Q_pelletloss` 本身依赖 A14，而 A14 依赖颗粒轨迹关联，关联又依赖 `v_sink_max` 标定与密集窗口。**
> **如果 A14 自身不可靠（`partial_window=True` / `coarse=True` / 关联未建立），`Q_pelletloss` 就没有资格去覆盖用户的显式声明。**
>
> 更严重的是**话术**：在 A14 不可靠时说"已按**实测值**覆盖您的声明"，等于**声称我们测到了某个东西，而我们并没有可靠地测到**——**这恰好违反了原则 1（不得给出无法兑现的承诺）**，而且是同一个盲区第四次出现。

**修正后的三段式判定：**

| A14 状态 | 实测 vs 声明 | 行为 |
|---|---|---|
| **A14 = ok** | 矛盾 | 采用实测，告知：「**实测显示存在显著沉降损失，已按沉性料规则处理。若您确认饲料为浮性，请检查 ROI.bottom_band 是否覆盖了排水口/溢流区**」 |
| **A14 = 降级/不可用** | 矛盾 | **不覆盖声明**，但**也不输出干净的 T90/T100**——标记 `sedimentation_risk_unverifiable`，按保守分支处理，告知：「**无法验证沉降损失（A14 不可用），已按保守方式处理**」 |
| 任意 | 一致 | 正常 |

> **关键原则：无法验证时，落到更保守的分支（更多告警），而不是保留用户那份"干净的"声明。**
> 注意两种情况的**动作相同**（都不给干净的 T90），但**理由与话术必须不同**——不能把"没测出来"说成"测到了"。

#### ⚠️ 专项：时间基准的两类风险（**VFR 是"尺子准不准"，`t0` 是"零点在哪"**）

##### 风险 A：VFR 帧率（我提出）

`RunMeta` 之外还有一个更隐蔽的输入风险：**视频帧率**。

- 手机/运动相机录制的视频常为 **VFR（可变帧率）**，容器的 `CAP_PROP_FPS` 只是标称平均值，**与实际逐帧时间戳不符**；
- 若我们按标称 FPS 推算 `t_seconds`，**时间轴会漂移**，而 **T50 / T90 / RR 观察窗 / 摄食起止时刻 / 所有速率指标全部建立在时间轴上**——**错了不报错，且无从察觉**。

**对策（工程要求）：**
1. **优先使用逐帧时间戳**（`cv2.CAP_PROP_POS_MSEC`）构建时间轴，而非 `帧序号 / 标称FPS`；
2. 若只能拿到标称 FPS，则标记 `timing_source='nominal_fps'`，并**在报告中显式提示"本视频时间轴基于标称帧率，若为 VFR 录像，所有时间类指标可能存在系统性偏差"**；
3. 自检：`标称时长 = frame_count / fps` 与实际解码时长偏差 >2% → 告警 `timing_suspect`。

> **这条与 §4.4 的 `dt_s` 列呼应**：`dt_s` 用的是**真实间隔**，因此逐帧积分天然正确；但若**时间轴本身**错了，`dt_s` 也救不回来。**时间基准必须先于一切时间指标被验证。**

##### 风险 B：`t0`（投喂起点）的定义（**PM 提出，我发现其方案仍缺一个维度**）

`t0` 至少有三种合理但**互不相等**的定义：

| 定义 | 枚举值 | 时刻 |
|---|---|---|
| A. 投饵器**启动** | `feeder_start` | 最早 |
| B. 第一颗饲料**离开投饵器** | `pellet_released` | 中间 |
| C. 第一颗饲料**出现在画面/入水** | `pellet_in_frame` | **最晚（默认）** |

**A 与 C 之间可能差 1–3 秒甚至更久。** 而 **T50 / T90 / 响应潜伏期全部以 t0 为零点**，定义不同则数值系统性偏移一个常数；**若两组视频的打点习惯不同，偏移在组间不一致，在报告上完全看不出来。**

**采纳 PM 的三条要求**：① 默认固定为 **`pellet_in_frame`**（可由视频客观判定、可复现、不依赖外部观察）；② `t0_definition` 写入 `run_config` 并参与 `compare.py` 校验；③ UI 打点时**必须提示当前使用哪个定义**，不允许"凭感觉点一下"。

##### 🔴 我补的第三个维度：**`t0_source`（自动 vs 手动）也必须进 `run_config` 并被校验**

PM 覆盖了 **定义** 维度，但**没覆盖"谁来定这个点"**——而契约里本来有一条"来源优先级：用户手动打点 > 自动检测"。**这两条放在一起有个隐患**：

> 若 run A 的 `t0` 是**自动检测**的、run B 是**人工打点**的，即使两者都用 `pellet_in_frame` 定义，也**可能系统性不同**（自动依赖检测器、人工依赖人的判断）。**跨组比较时同样失效。**

**更重要的是：自动检测 `t0` 的偏差与处理组相关——这是与自变量混淆的系统偏差。**

> 自动检测的判据是"颗粒数首次 >0 且持续"，**它依赖检测器召回**。
> - 饲料 A 分散快、颗粒清晰 → 检测器早早就检出 → `t0` 偏早
> - 饲料 B 易结团、初期颗粒稀疏 → 检测器漏检 → `t0` 偏晚
>
> 结果：**饲料 B 的 T50 被系统性缩短，看起来"被吃得更快的"**——而"分散快慢"恰恰可能与我们要测的诱食性相关。
> **这是与自变量混淆的偏差，比人工打点的随机偏差危险得多**（人工偏差至多是常数偏移或随机噪声，不会随处理组系统性变化）。

**因此采纳并强化契约的优先级规则**：

| 场景 | `t0` 取值策略 |
|---|---|
| **跨组比较（主场景）** | ⭐ **由同一人按固定定义统一打点**（避免与自变量混淆的检测器偏差）；自动检测值仅作交叉校验 |
| 单次分析 | 自动检测即可，但须记录 `t0_source='auto'` 并输出 `t0_detect_conf` |
| 两者都有 | **都记录**，偏差 >1 s 时告警 `t0_discrepancy` |

**工程要求**：`t0_definition` 与 **`t0_source`** 均写入 `run_config`，**`compare.py` 两者都要校验**。

> **与 VFR 风险是并列关系**：**VFR 让"每一秒有多长"不可信，`t0` 定义让"从哪一秒开始数"不可信，`t0` 来源让"这个数由谁定的"不可信。三者叠加时，时间指标会同时偏移且缩放——而且都不报错。**

**时间基准六类风险全表**（PM 补充 ④⑤⑥，形成完整清单）：

| 类 | 让什么不可信 | 性质 | 检测方式 |
|---|---|---|---|
| ① **VFR 帧率** | 每一秒有多长 | 帧间隔**抖动** | ✅ 可自检（`timing_suspect`） |
| ⑤ **慢动作/延时** | 每一秒有多长 | 🔴 **恒定缩放**，文件内部自洽 | ❌ **不可检测，只能问用户** |
| ④ **多段拼接/中断续录** | 时间轴**断裂** | 时间戳重置或跳变 | ✅ 可自检（`timeline_discontinuity`） |
| ② **`t0` 定义** | 从哪一秒开始数 | 需锁定枚举值 | 进 `run_config` |
| ③ **`t0` 来源** | 这个数由谁定的 | **自动检测偏差与自变量混淆** | 进 `run_config` |
| ⑥ **多机位对齐** | 两个时间轴是否同源 | 将来（一期不做） | 预留 `sync_method` / `sync_offset_s` |

> **⚠️ ④⑤⑥ 中有两条是我们自己诱导出来的**（PM 自我批评，我完全认同）：
> - 我们在素材清单里要求"投喂前空镜头 → 投喂 → 吃完"，**用户很可能拍成两段再拼起来**（④）；
> - 我们建议"沉性料用 ≥60 fps"，**用户很可能为此去开手机的慢动作模式**，反而让时间轴整体缩放（⑤）。
>
> **对策已进问卷**：拍摄建议写死「请选**高帧率录像**而**不是**慢动作」；Q3 新增"一镜到底 vs 多段拼接"一问，**最优解是空镜头与投喂过程录在同一个连续文件里**。
>
> ④ 的自检要求：`POS_MSEC` 序列须**严格单调递增**；出现回退或相邻帧间隔 >中位数 3 倍 → `timeline_discontinuity=True`，**断裂点之后的时间指标一律不输出**。

### 4.6 非时间维度的同类漏洞（v10 新增，回应 PM 的征询）

PM 问"还有没有**非时间维度**的同类漏洞"。有，我找到四类，其中第一类与 `t0_source` 是同一个病（**偏差与因变量混淆**），但发生在空间/计数维度。

#### 🔴 漏洞 1：鱼体重叠导致的**聚集度指标与因变量混淆**（我认为这是目前最严重的一个）

**机制**：高诱食性 → 鱼群**聚集更紧** → 检测框**重叠更严重** → 检测器把多条鱼**合并成一个框** → 点模式统计（ANND / MDC / R90 / FIFFB / D_peak）基于**错误的点数与位置**计算。

> **关键问题不在于偏差方向，而在于偏差大小取决于聚集程度——而聚集程度正是我们要测的东西。**
> 与 `t0_source`（检测器召回随饲料分散性变化）是**完全同一个病**：**测量误差的幅度依赖于被测变量本身**，因此**即使两组真实值相同，也可能测出显著差异**。

**对策**：
1. 新增质量信号 **`Q_overlap`**（框间 IoU 分布 / 重叠系数）；
2. 所有点模式指标在 `Q_overlap` 超阈值时打 **`fish_count_confounded`** flag（**进阻断清单候选**，需 PM 定夺）；
3. ⭐ **把"鱼数"纳入验证模式的真值对照**——契约 §7.1 目前只要求人工数**颗粒数**，建议**同时数鱼数**。
   **理由**：颗粒计数误差可以靠 `N0_meta` 兜底，**鱼数没有任何独立的交叉校验手段**，而 `P_fz`、RP、ANND、FIFFB 全部建立在它之上。

> 这条与难点 #2（鱼体重叠遮挡）是同一现象，但**性质不同**：#2 是"精度不够"，本条是"**误差与被测变量混淆，会伪造出组间差异**"。

#### 漏洞 2–4：`compare.py` 还缺三条校验规则

PM 定的两条拒绝规则（px_per_mm 不一致、metrics_spec_version 不一致）覆盖不足，补三条：

| # | 触发条件 | 行为 | 理由 |
|---|---|---|---|
| **3** | **模型 md5 不一致** | **拒绝全部比较**（而非仅部分指标） | 换了/重训了检测模型 → 检测行为整体改变 → **几乎所有指标都不可比**。这是 CV 的基本事实，比 `metrics_spec_version` 更根本 |
| **4** | **`window_s` 不一致，或任一 run 的 `window_truncated=True`** | **拒绝比较 RR 与所有清空时间类指标** | **RR@300s 与 RR@180s 不是同一个量**。目前 `window_s` 列有记录但 compare.py 未校验——有数据没规则 |
| **5** | **ROI 多边形不一致**（面积差 >5% 或 IoU <0.95） | **告警（不拒绝）** | 不同养殖单元时 ROI 本应不同（合法），**同一单元时则不可比**。系统无法判断是哪一种，因此**提示而非拒绝**——与"拒绝"的判定标准一致：**只有当补救成本极低（重跑 4 秒）时才拒绝；ROI 不一致可能是合法的，拒绝会误伤** |

> 第 5 条体现一条判定原则：**"拒绝"只用于"两个 run 本应可比但参数不一致"的情形；"告警"用于"可能合法、需要用户判断"的情形。**

#### 管线顺序约束

输入侧校验需要"第一遍指标"（A1 N₀、A14、Q_vis）先算出来才能反查，因此管线顺序为：

```
ingest（含时间基准校验） → 检测/跟踪 → 第一遍指标（A1 / A14 / Q_vis）
      → ★ meta_validation（输入侧校验，可能覆盖 pellet_type 等）
      → 其余指标计算 → 输出
```

**要求 `meta_validation` 的每次覆盖都写入 `warnings` 数组与 `capability_report.md`**——用户必须看到"系统改了什么、为什么改"。

### 4.7 第三类混淆：**非随机缺失**（v11 新增，PM 提出、我补工程对策与比较设计含义）

#### 机制：造成的是**缺失**而非偏差，因此比前两条更隐蔽

> **活跃度高（抢食激烈）→ 鱼游速快 → 运动模糊加剧 + 帧间位移增大 → `Q_track` 下降 / `Q_ids` 上升 → C 组（个体级指标）被 `capability.py` 整组关闭。**
> **即：游得越快 → 速度越测不准，乃至不可测。**

与前两条的关键区别：

| 类型 | 后果 | 可察觉性 |
|---|---|---|
| 颗粒重叠 → N₀ 低估 | **数值偏差** | 数还在、只是不准，用户至少能起疑 |
| 鱼体重叠 → 聚集度偏差 | **数值偏差** | 同上 |
| **活跃度 → C 组关闭** | **缺失** | 🔴 **用户看到"这组没有游速数据"，不会意识到缺失本身就是结果** |

> **我们恰恰在最需要测量的时候测量质量最差。** 而 C 组包含游速本身，于是**高诱食性组系统性缺失游速、低诱食性组可得**——"哪些指标被输出"不再是随机的，统计学上称**非随机缺失（informative missingness）**。

#### ⭐ 由此得出的通则（建议进 PRD）

> **降级与关闭机制本身也会产生混淆。**
> 只要触发降级的条件（`Q_track` / `Q_overlap` / `Q_det`）**与被测变量相关**，"哪些指标被输出"就不再是随机的。
> **设计质量门时，除了问"这个数准不准"，还必须问"这个门会不会只在一部分组里关上"。**

#### 我的三条补充

**① `disabled_with_reason` 必须带上"这可能是效应本身"的提示**

现有格式是纯机械的 `{"metric":"C1","reason":"Q_track=0.42 < 0.50"}`——**它没告诉用户这个缺失是有信息的**。改为：

> 「C 组（含个体游速）因 `Q_track=0.42 < 0.50` 未输出。
> ⚠️ **注意：`Q_track` 会随鱼群活跃度下降，因此本组缺失本身可能指示摄食活跃度较高，而非单纯的数据质量问题。请勿按随机缺失处理。**」

**② `compare.py` 第 7 条规则：可用集不同且由非中立门控触发 → 拒绝统计推断（不只是告警）**

> PM 的第 6 条要求"可用集不同即告警"，我认为对**非中立门控**触发的情形应升级为**拒绝统计推断**。
> **理由**：若用户在 10 个 run 中只对"碰巧有 C 组数据"的 7 个做检验，**等于以结果为条件做抽样**——这是典型的选择性偏差，且比数值错误更难被发现。
> **但拒绝必须给出出路**（沿用"报错不能把用户卡住"的原则）：报告应同时建议**改用 B1 组（鱼体无关型活跃度）进行比较**，理由见 ③。

**③ ⭐ 由 ① ② 推出的比较设计结论：B1 应作为跨组比较的主力**

对每个质量信号问一句"**这个 Q 会不会因为我们正在测的那个效应而变化**"（PM 的检查法），可得：

| 指标组 | 主要门控 | 门控是否中立 | 结论 |
|---|---|---|---|
| **B1 活跃度（鱼体无关型）** | `Q_interf` / `Q_motion` / `Q_fg` | ✅ **相对中立**（环境/外部条件） | ⭐ **唯一由中立门控守护 → 跨组比较主力** |
| A 颗粒 | `Q_det` | ⚠️ 非中立（受颗粒密度影响） | 需 `N₀` 双轨与 A14 校正 |
| B2 聚集度 | `Q_fdet` / `Q_overlap` | ⚠️ 非中立（受聚集度影响） | 打 `fish_count_confounded` 后仅作支持 |
| C 个体行为 | `Q_track` / `Q_ids` | 🔴 **非中立**（受活跃度影响） | 缺失具信息性，**不得用于跨组统计推断** |

> **重要区分**：**"指标本身随效应变化"是我们想要的（那正是信号）；"指标的误差或可得性随效应变化"才是混淆。**
> B1 的**值**当然随活跃度变化——这正是它作为指标的意义；但 B1 的**门控**（反光/相机稳定/前景占比）不随鱼的行为变化，所以它的**误差**是均匀的。**这就是 B1 能作为比较主力的原因。**
>
> **这也给了我们此前"L0 靠不看鱼的全局特征"一个全新的、独立的第二理由**——不只是"不需要检测器就能跑"，而是**"它的门控是中立的，不会产出非随机缺失"**。

#### 🔴 v12 修正：**"B1 整组中立"不成立，须细分到子指标级**

用 PM 的检查法深入到 `Q_fg`，发现两个问题：

**问题 1：`Q_fg` 非中立，且机制与直觉相反**

| 机制 | 说明 |
|---|---|
| ① 前景**不只含鱼** | 背景减除会把**饲料颗粒、水花、气泡**一并算入前景。**投喂后早期颗粒最多 → `Q_fg` 虚高** |
| ② **聚集 → 遮挡 → 投影面积下降** ⚠️ | **高诱食性（聚集紧）组的 `Q_fg` 可能更低，而非更高**（与我最初的猜测相反） |
| ③ 门控在**低端**触发 | `Q_fg < 0.01` 只在"几乎看不到鱼"时触发 |

**修复**：`Q_fg` 的计算区域**必须排除 `ROI.pellet_zone`**（或扣除已检测的颗粒区域）。否则 `Q_fg` 被颗粒数污染——**而颗粒数是 A 组正在测的量**，等于用一个被测变量去门控另一个指标。

**⭐ 但比修门控更重要的一条（PM 提出）**：
> **`Q_fg` 不只是门控，它可能是归一化因子。只要把活跃度按「鱼数」或「前景面积」归一化，就会引入混淆。**
> **规则：活跃度一律以固定的 `ROI.arena` 面积归一化，绝不以鱼数或前景面积归一化。**
>
> `arena` 是外部给定、与效应无关的量；鱼数与前景面积都随效应变化。
> **修门控只影响"什么时候不可用"；归一化错误会污染每一个数值。**

**问题 2：B1-5「群体平均游速」是归类错误**

| B1 子指标 | 门控 | 中立? |
|---|---|---|
| B1-1 帧差能量 | `Q_interf` / `Q_motion` | ✅ 中立 |
| B1-2 光流幅值 | `Q_interf` / `Q_motion` | ✅ 中立 |
| B1-3 傅里叶频谱 | `Q_interf` + 标定状态 | ✅ 中立（标定属外部条件） |
| **B1-4 混合熵** | `Q_fg` | ⚠️ 非中立，修复后近似中立但仍需标 `fish_count_confounded` |
| **B1-5 群体平均游速** | `Q_track` / `Q_ids` | 🔴 **非中立** |

> **B1-5 虽名为"群体平均"，但依赖逐条鱼的稳定跟踪，本质是 C 组指标做了群体聚合。已重归类至 C 组。**
> ⚠️ 这是"**行为与分类不一致**"——能力开关表里早已在高密度档把 B1-5 标 ❌，但归类没跟上。**这类不一致最容易被后来者误读**（他会以为它享受 B1 的中立待遇）。

**修正后的结论**：**B1-1 / B1-2 / B1-3 是唯一的"中立三兄弟"**，跨组比较主力应精确指这三项，而非整个 B1 组。

#### ⭐ v12 修正：我提议"上调 B1 至 P0"是错的，采纳 PM 的正交双轴方案

我此前基于"B1 是唯一中立组"提议上调 B1 优先级。**PM 反对，我认为她是对的**：

> **B1 测的是"活跃度"，而活跃 ≠ 摄食**——鱼可能因惊吓、水质突变而活跃。它是**更间接的证据**。
> 用户的核心问题（"哪种料更诱食""吃得多快"）由 **A 组（T50/T90/RR）+ B2 组 RP** 直接回答。
> **若把 B1 提到 P0 之上，等于用一个更间接的指标挤掉更直接的指标——为了可推断性牺牲了相关性。**

**正确做法是新增正交标签 `inferentially_valid`（`yes` / `conditional` / `no`），作为 schema 第 15 列：**

> **两个轴不应混为一谈：**
> **`P0/P1/P2` 回答"这个指标是否直接回答用户的问题"；**
> **`inferentially_valid` 回答"这个指标能否用于跨组统计推断"。**

| 指标 | `inferentially_valid` |
|---|---|
| **B1-1 / B1-2 / B1-3** | **`yes`** ⭐（唯一三项） |
| B1-4 混合熵 | `conditional` |
| A 组（颗粒） | `conditional`（需 N₀ 双轨 + A14 校正） |
| B2 组（RP / 聚集度） | `conditional`（需 `Q_overlap` 未触发） |
| **C 组（含重归类后的 B1-5）** | `no`（当由 `Q_track` 关闭时） |

**我的补充：`inferentially_valid` 必须由 `compare.py` 数据驱动消费，不得硬编码进逻辑。**
> 即 `compare.py` 读取该列并据此拒绝/放行，**而不是在代码里维护"哪些指标可推断"的清单**。
> 理由与"阻断清单必须版本化"同源：**判据数据化，新增指标时才不必改代码——否则每加一个指标就多一处漏改的风险。**

#### ⚠️ v13 修正：我 v12 的"单重 vs 双重"机制论证**不成立**（结论保留，理由更换）

我 v12 提出 ANND/MDC"除以 N 造成双重污染"。**PM 复核后指出该论证在理论上不成立，我接受**：

> **ANND 与 FIFFB 都随点密度缩放**（随机点格局下 ANND ≈ 0.5/√密度；Delaunay 平均周长同样 ∝ 1/√密度），**点丢失会让两者同向膨胀**，不是"一个双重、一个单重"。
> **`1/N` 只是把求和变成均值，它本身不构成第二个独立误差源。** 且 **MDC 反而可能更稳健**——鱼聚成一团时，合并产生的点仍落在团内，到质心的均值偏移很小。

**修正后的处理：不做理论裁定，改由真值实测决定**（PM 提出，采纳）：
> 验证报告按 `Q_overlap` **分档**给出 ANND / MDC / FIFFB 各自的「实测 vs 真值」误差曲线，**选谁为主由该曲线决定，不写死在代码里**。
> 这用的正是我自己刚定的那条原则——`inferentially_valid` 须由 `compare.py` 数据驱动消费、不得硬编码。**同一条原则、同一场景，就该用同一个处理。**

**过渡期建议**：以 FIFFB 为主，但依据**不是"单重污染"，而是它文献校验最强（r=0.945）**——这个理由经得起推敲。

#### 🔴 v13 新增（PM 发现，我认为是本轮最重要的）：**偏差方向是"向零衰减"，会压缩剂量-响应曲线**

> 重叠导致的膨胀是**向零衰减**的：
> - 真值：高诱食性组聚集紧（ANND 小）vs 低诱食性组分散（ANND 大）
> - 实测：高诱食性组重叠重、膨胀多；低诱食性组膨胀少
> - ⇒ **实测组间差 < 真实组间差，效应被系统性削弱**

**这与我们此前处理的所有混淆性质相反**：

| 类型 | 后果 | 实例 |
|---|---|---|
| **假阳性方向**（伪造差异） | 让你得到**假结论** | N₀ 低估、t0 来源、鱼数混淆、非随机缺失 |
| **假阴性方向**（掩盖效应） | 让你**错过真结论** | 🔴 **本条：重叠导致的向零衰减** |

> ⭐ **最恶劣的推论：衰减幅度与效应大小成正比 ⇒ 会压缩剂量-响应曲线。**
> **在剂量梯度实验（问卷 Q18）中，这会让真实存在的剂量效应看起来更平，甚至呈现假的平台期。**
>
> **在筛选诱食剂的研发场景里，假阴性的代价可能高于假阳性**——前者让你**筛掉一个其实有效的诱食剂**，后者至少还能被后续实验证伪。

**🔴 由此暴露的一个架构缺口：我们的质量体系全部是"防假阳性"的**

> 所有 `blocking_flags` 的含义都是"**这个数值有已知缺陷 → 别信它**"。
> **没有任何机制提示"真实效应可能被掩盖"（防假阴性）。**
> **而用户的核心场景是"筛选诱食剂"——漏掉一个有效的，代价极高。**

**我的工程对策（三条）：**

1. **新增报告级（非指标级）告警区：「效应可能被低估的情形」**
   > 注意这是 **report 级**而非 metric 级：它判断的是**跨 run 的模式**，不是单个数值的缺陷，因此不属于 `blocking_flags`，应独立成节。
2. **可计算的诊断量：报告 `corr(处理/剂量水平, Q_overlap)`**
   > 若剂量越高、`Q_overlap` 越大（剂量→聚集→重叠），**则该相关性本身就是衰减偏差的证据**。
   > 触发条件：`corr > 0.5` 且 `Q_overlap` 跨组差异显著 → 在报告中显式提示"**平坦的剂量-响应曲线不能作为『无效』的证据**"。
3. **真值采集须覆盖剂量/效应两个极端**（对 §7.1 的补充）
   > 除了"鱼群聚集最紧的时刻 ≥2 帧"，**剂量梯度实验还需在低剂量端与高剂量端各采真值帧**——**压缩差异最大的地方就在两端**，只采中间测不出这个偏差。

#### ⚠️ v13 修正：RP 的**分子**不安全（PM 指出我漏了）

我 v12 说"RP 分母是基线期鱼数、效应无关，故安全"。**分母对，但分子被漏了**：

> `RP = mean(试验窗 N_fz) / 基线期 N_fz`
> **分子 `N_fz` 是在效应发生期间测量的，同样受重叠影响。**
>
> ⇒ **RP 仍需按 `fish_count_confounded` 处理**，只是不存在"分母也被污染"这第二层。
> `P_fz` 同理：分母是用户声明的常数（安全），**分子 `N_fz` 不安全**。

> **这不是吹毛求疵**：**RP 是 P0 主指标**，若因"分母安全"就判定它整体安全，**会在最关键的指标上漏掉防护**。
> 且注意：**RP 的分子低估同样是"向零衰减"方向**（高诱食性组聚集重 → 分子被低估更多 → RP 被压低 → 压缩组间差）——与上一条**方向一致、互相印证**。

> **（v9，PM 提出）单测应分两类。** 契约 §7 的 9 个场景本质都在断言"**算出来的值对不对**"；但按 §0.5 的推论（**"测试通过"在本项目不是有效质量信号**——单测能验证"算对了"，验证不了"意思对了"），还应该有一类断言：**"输出的边界/标记/话术对不对"**。
> **A 类测数值正确性，B 类测有没有撒谎。** 后者才是本项目风险更集中的地方。

**设计要点**
- `metrics/` 是**业务核心，必须独立且可单测**——检测模型可以换，指标定义不能乱。
- **★ `group_b1/`（活跃度）与 `group_b2/`（聚集度）必须保持两个独立模块，`aggregator.py` 严禁合成为单一标量。** 二者在诱食性强时呈**相反方向**（活跃度↑ / ANND↓），合成会抹掉最强判别信号。
- **★ `core/metric_value.py` 是全局约束点。** 契约里"不得用 0 填充 / 严禁默认为 0 / 失效须给原因"等禁令，全部收敛到 `MetricValue` 的构造期校验里，**写错了构造不出来**，而不是靠工程师记得遵守。
- **★ `quality.py` 与 `capability.py` 是一等公民，不是附属品。** 每个指标输出必须带质量分与适用条件；高密度/浑浊时由 `capability.py` 主动降级并明示，而不是硬凑数。这直接对应 §0.4 的三条工程纪律。
- **★ N₀ 估计独立成模块**（`group_a/n0_estimator.py`）：双轨校验（视觉平滑峰值 vs 元数据推算），偏差 >20% 告警。这是最隐蔽的偏差源（难点 #9）。
- **★ 非对称采样是硬设计，不是优化**（决策 3）：早期段必须密到能支撑颗粒关联，否则 A14 不可算、T90/T100 失去校正依据。
- `detectors/` 用统一接口 `base.py`，使 YOLO / SAHI / YOLOE / 传统CV 四种实现可插拔互换（这正是冷启动分层架构的落点）。
- `runs/<timestamp>/run_config.yaml` 是**可复现性的锚点**，也是横向比较的前提（不同饲料必须用同一份 config）；由 `export/compare.py` 做硬校验。
- `configs/profiles/` 支持"场景预设"，用户换池型时一键切换。

## 8. 面向「户外池塘 + 科研级对比」的场景化适配方案（v14 新增）

> 依据：用户四项决策（浮性膨化料 / 户外池塘网箱 / 愿标注 20–50 帧 / 科研用途进论文）。
> 本节只写**因场景变化而必须改的部分**；未提及的部分沿用 §1–§7。

### 8.1 🔴 先说结论：哪些原设计**失效**了

我在 v1–v13 里隐含了三个前提，户外场景全部不成立：

| 隐含前提 | 户外的实际情况 | 后果 |
|---|---|---|
| 相机固定、俯拍或接近俯拍 | 岸上/池边**斜拍水面**，视角浅、透视畸变严重 | 尺度不一致、颗粒沿视线方向**互相遮挡** |
| 水体相对清澈、鱼可见 | **水面反光**使水下鱼基本不可见 | **鱼体检测不可用** → B2/C 组指标失效 |
| 光照稳定、水面平静 | 阳光直射 + 镜面反射 + **持续波浪** | 帧差/光流被波浪与光照漂移淹没 |

**三条直接的连锁反应：**

1. ❌ **L0「背景减除 + 斑点检测」冷启动路线在户外不成立** —— 四个独立失效原因（见 §8.7）。
   **改为直接走 L1：用户标注 20–50 帧 → 微调检测器。**（用户已同意标注，此路可行）
2. ❌ **鱼体检测在户外斜拍下基本不可行** —— **不是"精度低"，是"大部分帧看不到鱼"**。
3. ⚠️ **B1-1 帧差能量（原活跃度主力）在波浪下失效** —— 需替换为抗波浪方案（§8.6）。

### 8.2 ⭐ 诚实的可行性评估：户外斜拍下颗粒计数的精度

> **这是必须如实告知用户、不能过度承诺的部分。**

#### 能做（预期精度）

| 条件 | 单帧计数相对误差 | T50/T90/RR 等比值·时间指标 |
|---|---|---|
| **理想**（阴天漫射光 / 有浮框 / 水面平静） | **±5–10%** | **±5–15%** |
| **典型**（多云或斜射光 / 有浮框 / 轻微波浪） | **±10–20%** | **±10–20%** |
| **较差**（晴天直射 / 无浮框 / 中风浪） | **±25–40%** | ±20–35%，**勉强可用** |
| **恶劣**（正午强反光 / 大风浪） | **> ±40%** | ❌ **不可用** |

> **关键认识：比值/时间类指标（T50、T90、RR）比绝对计数稳健得多**——它们不依赖绝对计数的准确性，只要求偏差在整段视频内**稳定**。
> **所以主结论应当只用比值/时间指标，绝对颗粒数仅作为参考量输出并标注误差范围。**
> **同一视频内部的相对变化（衰减曲线形状）是可靠的**；跨视频的绝对数比较不可靠。

#### 做不到（必须明确告知）

| # | 做不到的事 | 原因 |
|---|---|---|
| 1 | **不能给出精确的绝对颗粒数**（如"剩余 137 颗"） | 斜拍遮挡 + 粘连 + 反光区不可见 |
| 2 | **不能在强反光 / 正午直射 / 大风浪条件下工作** | 误差 >40%，信噪比 <1 |
| 3 | **斜拍造成的物理遮挡无法恢复** | **单应性变换只解决"尺度不一致"，不解决"物理遮挡"**——投影变换不能还原被遮住的信息 |
| 4 | **不能跨不同光照/天气/时段的视频做绝对数比较** | 只能比较归一化后的比值与时间指标 |
| 5 | **不能可靠地检测鱼体** | 水面反光使水下鱼不可见（见 §8.3） |
| 6 | **不能区分"被吃掉"与"消失在反光区/被波浪暂时淹没"** | 只能处理"漂出 ROI 边界"这一种情形 |
| 7 | **不能保证 20–50 帧标注覆盖所有条件** | 若视频的光照/天气跨度大，需扩充标注 |

> **⚠️ 最需要如实传达的一条：**
> **户外池塘斜拍 + 浮性料 ⇒ 我们只能可靠地测「颗粒消失的速度」，不能可靠地测「鱼的行为」。**
> **主结论必须建立在 A 组颗粒曲线上；行为类指标（B/C 组）在户外应默认关闭或仅作探索性参考，不得进入论文主结论。**

### 8.3 🔴 鱼体检测在户外为何基本不可行（及这带来的新混淆）

- 浮性料漂在**水面**，鱼在**水下**抢食；
- 斜拍 + 水面**镜面反射** → 晴天时水面像镜子，**水下的鱼几乎完全不可见**；
- 鱼只在**冲到水面抢食的瞬间**才可见。

**这引入一个此前未识别的混淆（且是最强的一档）：**

> **鱼的可见度 ∝ 摄食活跃度。**
> 高诱食性组 → 鱼频繁冲到水面 → 可见度高 → 检出多；
> 低诱食性组 → 鱼不上来 → 可见度低 → 检出少。
>
> **这既是"因变量混淆"（N_fish 随效应变化），又是"非随机缺失"（低诱食性组根本看不到鱼）。**

**结论：B2 组（聚集度、RP、集鱼率）与 C 组（个体行为）在户外斜拍下不可用。** 若要启用，必须同时满足：阴天/清晨低反光时段 + 高机位接近俯拍 + 用户接受其仅作探索性参考。

### 8.4 ⭐ 最高性价比的改进：**浮动投喂框**（一个硬件解决四个问题）

**强烈建议用户加装一个漂浮的限定框（PVC 管 / 泡沫浮框 / 竹框，成本几十元）：**

| 解决的问题 | 说明 |
|---|---|
| ① **漂出率大幅下降** | 颗粒被限制在框内，"漂出 vs 被吃掉"的歧义范围从整池缩小到框边界 |
| ② **ROI 明确** | `pellet_zone` 直接由框定义，无需人工猜测 |
| ③ **透视标定有明确参照物** | **框的四个角就是单应性变换的四个标定点**——标定与 ROI 一次完成 |
| ④ **限制颗粒密度** | 框内面积已知，**单位面积颗粒数可控** → 预知重叠程度，可设计投喂量使重叠可接受 |

> **这是整个方案里投入产出比最高的一条建议。** 若用户暂时不装，则漂出率会显著上升、ROI 与标定都要靠人工估计，精度落在"较差"档。

### 8.5 透视校正：单应性变换（能力边界要说清）

**做法**（OpenCV，`cv2.findHomography` + `cv2.warpPerspective`）：

1. 用户在首帧标出**投喂框四角**（或已知尺寸标定板四角）；
2. 给出框的**实际边长**（米）；
3. 计算 3×3 单应矩阵 `H`，把该四边形映射为矩形（俯视平面）；
4. 后续所有帧用同一 `H` 做 `warpPerspective`（**机位固定时 H 只算一次**）；
5. 在校正后的平面上做检测、计数、面积测量、轨迹分析。

**能力边界（必须写清楚，否则会被误用）：**

| 能解决 | ❌ 不能解决 |
|---|---|
| 同一物体在画面近/远处**尺度不一致** | **物理遮挡**（前颗粒挡住后颗粒）——投影变换无法还原丢失的信息 |
| 面积/距离可测 → 可用**统一的面积阈值**过滤 | 因遮挡导致的**漏检** |
| 轨迹在"水面坐标系"中可比 | 反光区内的信息缺失 |

**未标定时的降级**：所有 mm/BL 量纲自动降级为像素口径，并标 `unnormalized`（不可跨视频比较）——沿用 §4.4 `unit_scale` 的校验逻辑。

### 8.6 ⭐ 颗粒计数：密集时用**面积积分**，稀疏时用**检测计数**

斜拍 + 浮性料聚集 → 密集处粘连严重、逐个检测必然漏检。**引入第二种计数法：**

```
稀疏段：N_detect  = 检测器逐个计数（准确）
密集段：N_area    = A_foreground / A_single   （对部分遮挡不敏感）
```

- `A_single`（单颗平均投影面积）**从"无鱼纯饲料"标定视频中测得**（我们已在素材清单里要了这段视频）；
- **关键洞察：`t≈0` 颗粒最密集，正是面积积分法最适用的场景——这恰好针对了难点 #9（N₀ 系统性低估）**；
- 稀疏段（衰减后期）用检测计数（此时准确）；
- **过渡区两者都算，偏差 >20% 时告警**（与 `Q_n0gap` 同样的双轨思路）。

> **这使得 `00_calibrate_pellet_dynamics.py` 的产出需要调整**：浮性料场景下 **`A_single` 比 `v_sink_max` 更重要**；`v_sink_max` 降级为可选（浮料吸水后长时间仍会缓沉，保留但不强制）。

### 8.7 反光与波浪：组合拳

#### 硬件侧（成本低、收益大）

| 措施 | 说明 |
|---|---|
| ✅ **CPL 偏振镜**（必备，几十元） | 水面反光是**部分偏振光**，CPL 可显著抑制，是单条性价比最高的措施 |
| ✅ **拍摄时段** | 清晨 / 傍晚 / 阴天；**避开正午**（太阳高度角大 → 镜面反射最强） |
| ✅ **机位抬高** | 越高越接近俯拍，既减少镜面反射路径，又减轻斜拍遮挡与透视畸变 |
| ✅ **避免逆光** | 让太阳在拍摄者身后 |
| 🔶 **近红外（NIR）** | 评估见下 |

**近红外是否值得推荐？——我的判断：作为 P1 升级路径，不作 P0。**
- 原理：水体在 >700 nm **强烈吸收**（近乎全黑），而饲料（有机物）反射较强 → **对比度极高**；且不受可见光波段的许多干扰；
- 代价：需去除 IR-cut 滤镜的摄像头，或 NIR 工业相机 + 850 nm 滤镜（几百元量级）；
- **建议**：先以「可见光 + CPL」跑一轮并量化精度；**若典型条件达不到 ±20%，再升级 NIR**。这条路径有明确的决策点，不必一开始投入。

#### 算法侧

| 措施 | 说明 |
|---|---|
| **反光掩膜** | 高亮度 + 低饱和度区域检测 → 生成掩膜，`Q_interf` 统计其占比；掩膜内的颗粒消失记为 `lost_in_glare`（unknown，**不猜测**） |
| **参考区逐帧扣除**（PM 的 P0-FR-13） | 见 §8.8 |
| **CLAHE** 光照归一化 | 缓解局部明暗差异 |
| **多帧中值/最小值合成** | 抑制**瞬时**高光（sun glitter 是闪烁的，多帧最小值可压掉）；注意颗粒是静止或缓动的，不会被误压 |
| **HSL/RGB 色彩不变式** | 减弱光照强度变化的影响 |

### 8.8 ⭐ 活跃度指标：户外用**空间异质性**替代全画面帧差

**PM 的问题是：户外波浪下"帧差能量"是否还可靠？我的答案是：原始的 CVFAI 全画面帧差在户外不可靠。**

原因：波浪本身就是持续的背景运动，且**风力随时间变化**，所以：
- 帧差基线高且**不稳定**；
- **投喂前基线期不能代表全程的噪声地板** → 我们原来的 `μ_base ± 3σ_base` 判据失效。

**PM 的"参考区实时噪声扣除"（P0-FR-13）方向正确，我采纳并补充两点：**

1. **必须逐帧扣除，不能事后归一化**：
   `M_diff_corrected(t) = M_diff(feed_zone, t) − α · M_diff(reference_zone, t)`
   参考区 = 同条件水面、无鱼无料、尽量与投喂区等距等深。
   `α` 由基线期回归得到（不是拍脑袋）。
2. **比参考区扣除更关键的是"空间异质性"判别**：

> ⭐ **波浪与摄食扰动在"空间分布形态"上本质不同：**
> - **波浪** → **空间均匀**（整个水面一起起伏）；
> - **摄食抢食** → **空间局部集中**（少数位置剧烈扰动）。
>
> **因此用"空间不均匀性"来判别，比用"总能量"稳健得多。**

**实现（低成本、纯 OpenCV）**：
```
将投喂区划分为网格（如 16×16）→ 逐格计算帧差/光流幅值 → 计算该分布的形状统计量：
   · 峰度 kurtosis（摄食时尖峰高）
   · 基尼系数 / 变异系数（摄食时不均匀）
   · 前 5% 格子能量占比（摄食时集中）
```
> 这些量**对全局性的波浪不敏感**（波浪会均匀抬高所有格子的值，不改变分布形状），这正是我们要的性质。

**户外活跃度指标优先级（修订后）：**

| 指标 | 户外可用性 | 说明 |
|---|---|---|
| **A 组 颗粒曲线** | ✅ **主结论** | 最可靠，不受波浪直接影响（颗粒检测看形状/纹理，不看运动） |
| **空间异质性指标**（新） | ✅ 辅助 | 抗波浪，建议实现 |
| **B1-3 傅里叶频谱 + 参考区扣除** | 🔶 探索 | 本为水面设计，理论上适配；但需 SVM 标定（≥20 段），未标定时只能输出 `calibrated=False` 的比值 |
| **B1-1 CVFAI 原始全画面帧差** | ❌ **户外不用** | 波浪污染，信噪比不足 |
| **B1-2 光流幅值（全画面）** | ❌ **户外不用** | 同上；即使扣全局漂移，波浪的空间非均匀性仍会残留 |
| **B2 / C 组** | ❌ **户外不用** | 鱼体检测不可行（§8.3） |

### 8.9 ⚠️ 背景建模：户外**放弃**背景减除作为颗粒检测主方法

这是与 v1–v13 的一处**重大路线修正**。原 L0 方案（MOG2 背景减除 + 斑点检测）在户外有**四个独立失效原因**：

1. **波浪** → 每帧背景都在动 → 前景掩膜大面积误检；
2. **光照漂移** → 背景模型需要自适应；
3. **但自适应会吸收静止目标** ⚠️ **这是致命矛盾**：浮性料在无风时**静止漂浮**，自适应背景模型会把它们学成背景 → **漏检**；
4. **反光闪烁** → 高亮斑被判为前景 → 误检。

> **结论：户外场景下，颗粒检测必须以「微调后的检测器」为主（YOLO + SAHI），背景减除只能作为辅助或用于 `Q_fg`/参考区统计，不能作为冷启动主路线。**
> **相应地，冷启动路径改为：用户标注 20–50 帧 → 微调 → 检测。**（用户已同意标注，可行。）

### 8.10 标注策略：**点标注**（使 20–50 帧标注量可行）

**问题**：户外单帧可能有上百个颗粒，20–50 帧 × 100 颗粒 = 2,000–5,000 个目标。
**用 bbox 逐个框选极慢**（估计 3–6 小时），会直接劝退用户。

**方案：点标注（每颗点一下）→ 自动生成训练框**

```
用户在 Label Studio 中：每个颗粒点一个点
        ↓ 转换脚本
以点为中心，按标定得到的 A_single 半径生成正方形/圆形 bbox
        ↓
YOLO 格式数据集 → ultralytics 微调
```

- **点标注比 bbox 快 3–5 倍**，20–50 帧的标注量降到约 **40–80 分钟**，可接受；
- 生成框的半径来自 `A_single`（标定视频测得），与 §8.6 的面积积分法**共用同一个标定值**，一致性好；
- 若用户视频的颗粒在画面上大小差异大（斜拍！），**按透视位置（距相机远近）用不同的半径** —— 由单应性变换的尺度场推出。

**标注工具选型**（team-lead 问到）：

| 工具 | 颗粒级极小目标友好度 | 结论 |
|---|---|---|
| **Label Studio** | ✅ **点标注配置最灵活**，支持视频插帧，pip 安装免 Docker | ⭐ **推荐** |
| CVAT | 🔶 强大但需 Docker，小目标需放大操作，配置点标注略繁琐 | 备选（标注量 >2000 帧时再迁） |
| Roboflow | 🔶 云端，标注体验好但数据要上传 | 不用（科研数据本地化要求） |

**微调入口**（用户标注后一键执行）：
```bash
python scripts/03_finetune.py --data datasets/yolo/pellet/data.yaml \
       --base yolo11m.pt --epochs 80 --imgsz 1280 --device 0
```
Gradio UI 中提供「开始微调」按钮封装同一入口。**`imgsz` 建议 1280（小目标必需，算力完全够用——见 §3.6）。**

### 8.11 科研工作流：统计层与可复现性

#### 统计库选型（team-lead 问到）

| 库 | 用途 | 结论 |
|---|---|---|
| **pingouin** | `pg.ttest` / `pg.mwu` / `pg.anova` / `pg.pairwise_tukey` / `pg.welch_anova` / `pg.mixed_anova`，**直接返回效应量 + CI** | ⭐ **首选**，API 最贴近科研需求，一行给出 d + CI |
| **statsmodels** | `MixedLM`（混合效应）、`multipletests`（多重比较校正）、回归 | ⭐ **必备补充**，混合效应模型 pingouin 覆盖不全 |
| scipy.stats | 基础检验、`tukey_hsd`（≥1.7） | 底层依赖 |

> **推荐组合：pingouin（主）+ statsmodels（混合效应/多重比较）+ scipy.stats（底层）。**

#### 🔴 一个必须提醒用户的统计陷阱：**伪重复（pseudoreplication）**

> **在同一口池塘/同一个网箱重复投喂 5 次，不等于 n=5。**
> 真正的独立样本是**池塘/网箱数**，不是投喂次数。若把重复投喂当独立样本做 t 检验，会**低估标准误、夸大显著性**——这是生物学论文被拒稿的常见原因之一。
>
> **对策**：默认按「**池塘/网箱 = 随机效应**」建模（`statsmodels.MixedLM` 或 `pg.mixed_anova`），并在 UI 中强制用户声明重复结构。
> **这也是我把"两组 vs 剂量梯度"视为关键待确认项的原因**——两者的统计模型不同，但**伪重复问题两者都存在**。

#### 关于"剂量梯度 vs 两组"是否需要现在就按可扩展设计

**我的判断：统计层应按可扩展设计，但不必现在实现。**
- 结构上：比较逻辑抽象为「**比较计划（comparison plan）**」对象，描述"哪些 run 属于哪组、按什么模型检验"——两组只是它的一个特例；
- 这样 P1 加剂量梯度时，只需新增一个 plan 类型，**不动比较框架**；
- **成本几乎为零，但不做的话后期要重构比较模块。建议现在就做这层抽象。**

#### 批量 / 盲法 / 可重入

- **批量**：多视频队列 + 组标签；每视频独立输出 `runs/<id>/`，跨 run 比较由 `compare.py` 完成；
- **盲法**：分组标签在分析阶段以**编号**呈现（`run_001`…），分组映射表**单独加密存储**，揭盲需显式操作并写入审计日志（与 `run_config` 同级留档）；
- **可重入**（PM 问到）✅ **我的架构天然支持**：管线分层为 `抽帧 → 检测/跟踪 → 指标聚合 → 导出`，若把中间产物落盘：

```
runs/<id>/
├── cache/detections.jsonl      # 逐帧检测 + 跟踪结果（含 conf / bbox / track_id）
├── cache/quality.json          # 13 个 Q_* 质量信号
├── metrics/                    # ← 指标层，可仅凭 cache 重算（秒级）
└── export/                     # 最终产物
```
**人工修正时序数据后，只重跑 `metrics/` 层，不重跑检测/跟踪。** 这是分层设计的直接收益，无需改动架构。
